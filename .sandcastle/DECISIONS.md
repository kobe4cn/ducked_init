# 遇到要拍板的设计决定

无人值守运行时没有人回答问题。prep、implementer、reviewer 遇到票和指引都没写到的设计决定，先按下面判断属于哪一类。

## 必须停下（交给人）

满足任一条：

- 要改 ADR 定下的方向或原则，或者和某条 ADR 冲突
- 改公共接口（HTTP 路由、工具的输入输出、导出给别的模块用的函数签名）的语义，或改数据库 schema、迁移
- 涉及权限、租户隔离、凭据、敏感字段的处理
- 删除或改写用户数据
- 几个选项都难以撤回，或者你给不出明确的推荐

## 可以代拍板（按推荐做，事后由人确认）

不属于上一类，并且满足任一条：

- 有一个选项是**收窄范围**：本票做能做稳的部分，没做到的记进 `KNOWN_GAPS` 或测试里的 expected fail，另开后续票
- 局部取舍：只影响本票改到的模块、以后改回来代价小（比如某个阈值、命名、内部数据结构、两种都说得通的实现方式）

代拍板时：

1. 选你推荐的那个。拿不准选哪个时，选范围更窄、更容易撤回的那个。
2. 在 issue 上留一条评论，第一行是 `<!-- sandcastle:decided -->`，写清：要决定什么、有哪几个选项、选了哪个、为什么。人不同意时只回一句话就能改，所以把其他选项写全。
3. 收窄范围时：
   - 改票的验收标准，写明没做到的部分去了哪张票。
   - 开后续票：`## Parent` 写本票的父票（没有就写本票）、`## Blocked by` 写本票，加 `Sandcastle` 和 `ready-for-agent`。有父票时，把后续票加进父票的 `## Split into`。
4. 照常做完，不打 `sandcastle:stuck`。脚本落地时会给票打 `sandcastle:decided`，并把这些评论贴到 PR 上，人看过后去掉这个标签。

拿不准属于哪一类时，按「必须停下」处理。
