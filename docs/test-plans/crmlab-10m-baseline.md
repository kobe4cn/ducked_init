# crmlab 规模档基线（1000 万人）

机器：16 核、128 GB 内存，Apple `container` 跑 Postgres / MySQL / MongoDB（各 4 GB）/ SeaweedFS。租户 `crmlab-10m`，配额 16 线程、65536 MB。
造数：`seed.ts --persons 10000000 --set 10m`；配置：`setup.ts --tenant crmlab-10m --set 10m`；核对：`verify.ts crmlab-10m --set 10m`。
测什么、关注什么风险见 `crmlab-plan.md` 的 T10。

### 首次合并的分解

映射是**串行**合并的，总耗时约等于各映射之和。耗时与行数关系不大：

| 映射 | 行数 | 耗时 | 行 / 秒 |
|---|---|---|---|
| events → event | 2.84 亿 | 582 s | 49 万 |
| order_items → order_item | 6,846 万 | 136 s | 50 万 |
| points_ledger → points_transaction | 4,115 万 | 130 s | 32 万 |
| orders（商城）→ order | 3,423 万 | 23 s | 150 万 |
| sale_items → order_item | 2,585 万 | 13 s | 196 万 |
| coupons → coupon | 1,261 万 | 11 s | 119 万 |
| members（会员中心）→ customer | 631 万 | 158 s | 4 万 |
| memberships → membership | 631 万 | 63 s | 10 万 |
| signups → customer / event | 56 万 | 57 s / 57 s | 1 万 |
| attendances（源视图）→ event | 34 万 | 52 s | 0.6 万 |

约一半的映射有 50–65 秒的「底价」，与行数、是否含敏感列都无关（56 万行的活动报名 57 s，1,261 万行的券 11 s）。原因待查：可能是每个映射的固定开销（提交、关系或唯一性检查），也可能是与同时进行的同步核对争用。查清前不开 issue。

customer 映射普遍偏慢（4–6 万行 / 秒），可能与身份打通前的敏感字段规范化 + 哈希有关，同样待查。

## 正确性（verify.ts，用时 48 秒）

全部一致，没有 ✘：

- 身份打通：3,026.6 万条源记录，缺失、被拆开、误合并、多出都是 0；统一消费者 11,821,387 = 期望。
- 标准层 15 个实体的行数与金额全部与真值一致。
- 11 个指标、4 个标签逐行一致（重算全部 15 个用时 107 秒，并发 4）。
- 探针在千万级下的取值与 5 万人档相同。

已知缺口在规模下的量级：`views_7d` 窗口内的匿名浏览约 199 万次，其中 183 万次能经设备归属到人，平台现在都不计（#154）。
