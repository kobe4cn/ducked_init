# crmlab 规模档基线（1000 万人）

机器：16 核、128 GB 内存，Apple `container` 跑 Postgres / MySQL / MongoDB（各 4 GB）/ SeaweedFS。租户 `crmlab-10m`，配额 16 线程、65536 MB。
造数：`seed.ts --persons 10000000 --set 10m`；配置：`setup.ts --tenant crmlab-10m --set 10m`；核对：`verify.ts crmlab-10m --set 10m`。
测什么、关注什么风险见 `crmlab-plan.md` 的 T10。

#### 分步计时（#161，2026-10-11）

合并结果的每个映射带 `steps`（毫秒），工作进程每合并完一个映射打一行 `[合并] <源表> → <实体>（<映射 ID>）：…`。
records 在增量合并时包括删旧的当前记录和插入新的当前记录；deleteInsert 包括删除本映射在标准层的旧行和插入新行。下表是新租户 `crmlab-10m-b` 从零首次合并的数字（单位 s；括号里是同一天 `crmlab-10m` 全部强制重建时的数字，只列差别大的）：

| 步骤 | signups → event（56 万） | attendances 源视图 → event（34 万） | members → customer（631 万） | users → customer（743 万） | order_items → order_item（6,846 万） | events → event（2.84 亿） |
|---|---|---|---|---|---|---|
| input（判断源表、读主键；源视图在这里物化） | 0.09 | 0.19 | 0.10 | 0.10 | 0.10 | 0.14 |
| lastMerge + maxBatch | 0.02 | 0.01 | 0.02 | 0.02 | 0.02 | 0.04 |
| live（每条源记录取最新一版） | 0.58 | 0.17 | 4.2 | 6.1 | 6.7 | 62.5 |
| unknownValues | 0 | 0 | 0 | 0.01 | 0 | 0 |
| transform（含敏感字段规范化 + 哈希） | 0.09 | 0.09 | 1.1 | 1.7 | 3.1 | 20.2 |
| keys（KEYS / BEFORE / WINNERS / 统计） | 0.33 | 0.21 | 4.1 | 7.0 | 7.2 | 40.2 |
| ensureTable | 0.01 | 0.01 | 0.01 | 0.01 | 0.01 | 0.01 |
| records（写 silver_records） | 0.15 | 0.08 | 1.5 | 3.0 | 2.9 | 23.1 |
| deleteInsert（删本映射旧行、写标准层） | 0.11 | 0.06 | 1.4 | **39.4**（3.3） | 2.6 | 18.0 |
| unique（跨映射主键唯一，ADR-0024） | 0.16 | 0.12 | —（customer 不查） | — | 9.5 | **380.4** |
| mergeLog + commit | 0.03 | 0.03 | 0.03 | 0.03 | 0.04 | 0.08 |
| rows（数本映射在标准层的行数） | 0.04 | 0.04 | 0.05 | 0.04 | 0.04 | 0.30 |
| **合计** | **1.6** | **1.0** | **12.5** | **57.4**（23.8） | **32.1** | **544.9** |

全部 32 个映射（重建那次）各步合计：unique 403 s（48%，其中 events 368 s）、keys 139 s、live 131 s、deleteInsert 74 s、records 46 s、transform 38 s，其余各步加起来不到 10 s。

**50–65 秒的底价：在合并代码里不存在，两次复测都没有复现；下面关于成因的说法是推测，没有证据证实。** 每个映射与行数无关的固定开销（input、lastMerge、maxBatch、ensureTable、mergeLog、commit、rows）合计 0.2–0.4 s；
100 万行以下的 10 个映射首次合并都在 3.1 s 以内：最慢的 douyin_buyers → customer（95 万行）3.1 s，signups 两个映射 1.6 s / 2.1 s，3 个自定义实体各 0.2–0.3 s。
两次复测与第一轮用的是同一份数据、同样的合并代码（只多了计时），第一轮之后改动的只有建 schema 的位置（#155，每个任务只执行一次）。
第一轮同一个合并任务里，有底价的映射前后都没有别的任务在跑（只有开头 30 秒有一个 source.verify），可那一轮整体 CPU 只有约 160%、溢写 46 GB，
说明进程大部分时间在等 IO，而不是在算。推测最可能的原因是当时机器上的存储（SeaweedFS / 本机溢写盘）偶发变慢，复测里也见到同样的单步抖动
（users → customer 的 deleteInsert 一次 39 s、重建时 3 s；points_ledger 的 records 一次 33 s、重建时 4 s）。
另一个差别：第一轮的文件类源表还没有业务主键（#157 声明失败），events、signups、buyers、trades、dy_orders、users、contacts、chats、mass_sends 按整行区分记录，
但会员中心 members、POS sales 这些一直有主键的表同样慢，所以它解释不了底价。现在每个映射都带分步计时，再出现时能直接看出慢在哪一步。

**customer 偏慢：同样没有复现。** 首次合并 members → customer 631 万行 12.5 s（50 万行 / 秒），与其他实体同一量级；
敏感字段规范化加哈希在 transform 里，631 万行约 1.1 s，不是瓶颈。第一轮 158 s 与底价同一原因。

**自定义实体 78 s**：3 个映射合计 1.3 s，其余是合并任务结尾的关系检查与身份打通——这个任务虽然不带 customer 映射，仍整表重算了一次身份打通（复测 46 s）。

**真正的大头**是大共享表 event（2.84 亿行）上的跨映射唯一检查（380 s，占这个映射的 70%），其次是映射串行。按 #161 的分工另开票：
大共享表上的跨映射唯一检查与 DELETE、BEFORE 全表扫（#164）、不同实体的映射并行合并（#165）、silver_records 的双写（#166）、没改到 customer 的合并也重算身份打通（#167）。
DuckLake 提交（每次 20–80 ms）与 customer 哈希（见上）没有可省的，不开票。加密（ADR-0020）发生在写数据文件时，算在 records、deleteInsert 里，没有单独拆开（要拆就得有一个不加密的湖来对照）；这两步加起来占映射总耗时的 14%，即使加密占了大头也不是瓶颈，所以不开票。

#### 跨映射唯一检查复测（#164，2026-10-11）

唯一检查改为只拿本映射这次写入的键（WINNERS）去连接 silver 里**其他**映射的行，不再对整个实体表 GROUP BY；并挪到本事务改 silver 之前执行。
挪位置的原因：DELETE / INSERT 之后，DuckLake 在事务里给 silver 的基数估计只有约 5,000 行（实际 2.95 亿），优化器总把哈希表建在 silver 一侧，
signups → event（56 万行）因此要全表扫 event，unique 从 0.16 s 变成 6.9 s；改之前估计准确，哈希表建在 WINNERS 一侧，动态过滤按键范围跳过 event 的全部文件（读 0 个文件）。
其他映射的行不受本映射的 DELETE / INSERT 影响，所以先查后写结果不变。租户湖锁了配置，不能用 `disabled_optimizers` 强制方向。

`crmlab-10m` 上的数字（单位 s；「之前」是 #161 全部强制重建那次）：

| | 之前 unique | 现在 unique | 之前合计 | 现在合计 | keys | deleteInsert |
|---|---|---|---|---|---|---|
| events → event（2.84 亿，只重建 event 的 6 个映射） | 368–380 | **1.7** | 545 | **166** | 50.9 | 36.0 |
| events → event（32 个映射全部重建） | 368 | **5.1** | — | 235 | 71.3 | 35.1 |
| order_items → order_item（6,846 万） | 9.5 | 1.1 | 32 | 39 | 14.1 | 7.8 |
| points_ledger → points_transaction（4,115 万） | 6.4 | 0.13 | 36 | 162 | 6.7 | 86.8 |
| chats → event（811 万） | 1.1 | 0.07 | 13 | 11 | 4.5 | 1.0 |
| signups → event（56 万） | 0.16 | 0.02 | 1.6 | 1.7 | 0.46 | 0.14 |
| **32 个映射合计** | **403** | **7.6** | 840 | 1,293 | 168 | 507 |

- unique 达标：events → event 380 s → 2–5 s，32 个映射合计 403 s → 7.6 s。
- 32 个映射全部重建那次总耗时反而更长（1,293 s），多出来的全在写文件的步骤：deleteInsert 74 → 507 s、records 46 → 398 s。后半段十几个小映射（attendances 34 万行、signups → customer 56 万行等）的 deleteInsert 都卡在约 28 s，与行数无关，和第一轮的「50–65 秒底价」很像。
  同一天的复测里 SeaweedFS 两次中断：一次容器退出，一次所有可写卷同时写满（`volume … is oversized`），新卷 26 s 后才建好，期间写入被拒、合并失败；重启容器后 localhost:8333 的端口转发也断过一次。所以这次写入步骤的数字反映的是存储状态，不是合并代码；底价的成因要单独查存储。
- BEFORE（keys 步骤）与 DELETE（deleteInsert 步骤）照票里的范围决定没有动，events → event 上分别是 51–71 s 和 35–36 s，留给以后的票。

#### 重建时的 keys 与 DELETE（#168，2026-10-11）

改动：重建时不建 KEYS；inserted / updated / deleted 由 WINNERS 与 BEFORE 的一次 `FULL OUTER JOIN` 得出（原来是两次 ANTI JOIN 加一次 SEMI JOIN）；silver 不存在时不建 BEFORE。DELETE 没改。
测法：`crmlab-10m` 上 `rebuildEntity(…, 'event')`，一个工作进程（16 线程、64 GiB），期间没有别的任务，连跑两次。#169（写入步骤的固定耗时、SeaweedFS 写满卷）**还没修**，deleteInsert 的数字受存储状态影响。

events → event（2.84 亿行，只重建 event 的 6 个映射；单位 s）：

| | keys | deleteInsert | keys + deleteInsert | 映射合计 |
|---|---|---|---|---|
| 之前（#164） | 50.9 | 36.0 | 86.9 | 166 |
| 现在，第一次 | 43.3 | 57.7 | 101.0 | 200 |
| 现在，第二次 | 42.1 | 34.4 | 76.5 | 168 |

两次的统计都是 inserted 0、updated 284,493,904、deleted 0，与改之前的语义一致。

**没有降到 30 s 以内。** 在同一个租户湖上把 keys 和 deleteInsert 的几段 SQL 单独跑了一遍（16 线程、64 GiB，中间表放内存）：

| 片段 | 耗时 s | 说明 |
|---|---|---|
| BEFORE（`SELECT DISTINCT event_id` 本映射在 silver 的行） | 3.0 | 只读一列，DuckLake 按 `_mapping` 的文件统计跳过别的映射 |
| 原来的 KEYS（`DISTINCT` 去重键） | 1.9 | 本票省掉 |
| 统计：原来三个子查询 / 现在一次全连接 | 8.3 / 4.9 | 本票省约 3.4 s |
| WINNERS（每个去重键 `row_number` 取一行，带全部列） | 17.1 | 合并里在落盘压缩的 stage 库上建，比内存里慢，是 keys 的大头 |
| DELETE 本映射的行（事务里执行后回滚） | 18.7 | 见下 |

- keys 省下的 7–9 s 正好是 KEYS 加上统计少做的那部分。BEFORE 本来就只要约 3 s，不是瓶颈。keys 剩下的约 42 s 里，大头是 WINNERS 的去重排序。WINNERS 要写进标准层，不能省；本票的范围也不包括改它。如果要再降，只能在源表主键与去重键相同、没有取最新规则的时候跳过 `row_number`，那要另开一张票。
- DELETE 已经是按文件整片删的。重建前后对比 `ducklake_data_file` / `ducklake_delete_file`（快照 636 → 643）：event 的 6 个映射各自的数据文件（events 18 个，其余各 1 个，每个文件里 `_mapping` 的最小值等于最大值）全部结束、换成新文件，**删除文件一个都没写**。所以不需要 `SET PARTITIONED BY (_mapping)`。
  不过 DELETE 仍要 18.7 s：DuckLake 要逐行判断条件、数出删掉的行数，才知道整个文件都被删光了。这一步要读 18 个文件、2.84 亿行（加密的，ADR-0020），所以花时间。
  deleteInsert 剩下的约 16–39 s 是写 2.84 亿行新文件，两次相差 23 s，和 #169 记下的存储抖动是同一类问题。写入的耗时由行数和存储决定，合并代码这边没有可省的。

## 正确性（verify.ts，用时 48 秒）

全部一致，没有 ✘：

- 身份打通：3,026.6 万条源记录，缺失、被拆开、误合并、多出都是 0；统一消费者 11,821,387 = 期望。

- 11 个指标、4 个标签逐行一致（重算全部 15 个用时 107 秒，并发 4）。
- 探针在千万级下的取值与 5 万人档相同。
