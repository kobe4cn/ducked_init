## 0. 结论：多数据源的主键问题解决到哪一步

同一个主键值出现在几个映射里，业务上有四种意思，平台都要求**显式声明**，不猜（ADR-0024）：

| 业务上的意思 | fmcglab 里的例子 | 平台的做法 | 用例 | 结论 |
|---|---|---|---|---|
| **带来源区分**（编号各自独立，是不同的东西） | 小程序商城订单号、奶站账单号都从 1 开始 | 默认**独占**：撞键的映射合并失败、列出冲突键；体检建议「键空间」；声明 `key_space` 后主键写成 `mall:1` / `station:1`，引用字段同样声明，发布时检查一致 | K1、K1b | ✅ |
| **去重**（同一批对象从几条路进来，只留一行） | 天猫 / 京东 / 抖音订单既有平台导出，又在订单中台里 | 独占先拦住，体检判为「重复接入、可以建合并组」；建**合并组**（ADR-0032）后同一主键只留一行，合并记录给出重叠行数与各字段不一致数 | K2 | ✅ |
| **覆盖**（后到 / 较新的一边说了算） | 中台记了售后退款，平台导出仍是「已完成」；平台确认收货比中台晚 | 合并组的存活规则 **`latest`（按 `updated_at` 取最新）**：整行取较新的一边；一样新时按组员优先级。平台不做「悄悄覆盖」，覆盖是成员选的、有统计的规则 | K2a、K2b、T7 第二轮 | ✅ |
| **补齐**（几个系统各维护一部分字段） | 商品名称、品类、标价在 ERP，品牌、扫码积分在扫码平台；新品只在扫码平台 | 合并组的存活规则 **`coalesce`（逐字段按优先级取第一个非空值）**；`priority`（整行取最高优先级）可对比 | K3、K3b | ✅ |
| 主数据只在一处维护、别处只引用 | 天猫子订单的商家编码、京东 SKU 对照表都指向 ERP 的 SKU | 引用字段直接写 ERP 的主键；京东先用源视图换成商家编码；没填的记「未关联」 | K4 | ✅ |
| 同一个人在多个数据源 | 会员中心、扫码平台、奶站、三个电商平台、企微、地推表 | 消费者按 `(数据源, customer_id)` 区分，身份打通按 手机 > 邮箱 > 外部 ID（unionid）归并 | P01–P07 | ✅（占位号、代填号要自己清洗，#254） |
| 同一个人多源属性不一致 | 会员中心上海、奶站苏州、扫码平台杭州 | `silver._consumer` 每人一行，默认按 `updated_at` 取最新；customer 映射可配 `survivorship.priority` 指定「哪个源说了算」（ADR-0027） | K8 | ✅ |
| 同一个人多源同意不一致 | 会员中心同意短信，奶站后来撤回 | `silver._consumer_consent` 每人每渠道取最新、同一时刻撤回优先 | K5 | ✅ |
| 同一个映射内的多版本 | 订单中台同一订单号有旧版本文档 | 映射 `dedupe: { key, latest }` | K6 | ✅ |
| 测试数据、不相干的行 | 测试奶站、测试码、B2B 团购单 | 映射 `where` / 源视图只取需要的行 | K7 | ✅ |
| 引用别的数据源的消费者 | 商城订单、埋点、周期购的会员号属于会员中心；中台订单的买家属于各平台 | `customer_source: <数据源>`（ADR-0030）；一张表混着几个平台时，先按平台拆成源视图 | P01、K2 | ✅（有限制，见下） |

**还没解决、或有限制的地方**（详见第 7 节）：
- ~~源视图的 `view_key` 在同一批次里不唯一时平台任取一行，`dedupe` 的「取最新」失效，且没有任何提示（#253）~~ 已修复：写了这样的 `view_key`，空跑与合并时报错，列出重复的标识并提示去掉。本场景的买家视图不写 `view_key`。
- 「先合后拆」以后，退役 ID 的别名仍指向留下原 ID 的那个人：点查接口会返回别人的结果（#252）。发错一次映射就会触发。
- 身份打通没有「一个值连了太多人」的保护（#254）：奶站占位号不去掉时，267 位订奶户被并成一个人。
- 独占冲突的报错还在建议「加前缀或去掉一边」，没提键空间与合并组（#257）。
- 合并组每个实体最多一个、组员的键空间要相同；`customer_source` 对整列只能指一个数据源（订单中台一张表三个平台，要拆三个源视图）。本场景都能绕过，但配置量大，见第 7 节的建议。

## 1. 为什么另起一个快消场景

crmlab 是服装品牌，订单低频高客单，身份主要靠手机号。快消（乳品）的真实情况差别很大，而且正好压在平台最薄弱的地方：

| 快消的特点 | 平台要经得住的 |
|---|---|
| 大部分销量在商超、便利店，品牌看不到买的人；**一物一码**扫码是认识消费者的主要入口 | 扫码事件量是订单的数倍；扫码用户只有扫码公众号的 openid，一部分有 unionid、少数绑了手机 |
| 电商（天猫、京东、抖音）都经 **ERP / 订单中台**汇总，同一批订单两条路进来，售后在中台处理 | 合并组的「取最新」；一张中台表混着几个平台和 B2B 单 |
| **奶站订奶到户**、周期购：月账单、订阅卡 | 键空间（账单号从 1 开始）；自定义事实实体做指标；时区（每月 1 日 07:30 出账） |
| 线下地推、试饮，手填表单；**导购代填、占位号**很普遍 | 身份打通的数据卫生 |
| 商品主数据分散：ERP 有名称品类，扫码平台有品牌和扫码积分，电商用自己的 SKU | 合并组的「逐字段补齐」；SKU 对照表 |
| 经销商回传的**商超门店周销量**没有消费者 | 非消费者数据入湖、在工作台与扫码数据一起分析（扫码率、窜货） |
| 运营要的人群：扫码未购、品类偏好（奶粉人群）、周期购在订、流失预警 | 多指标标签；按品类的指标（#255，做不了） |

## 2. 场景：「禾川乳业」

### 2.1 租户与成员

正确性档 `fmcglab`（手工测试）与冒烟档 `fmcglab-smoke`（脚本）。成员：`admin@`（管理员）、`eng@`（数据工程师）、`an@`（分析师）、`view@`（查看者）。映射、源视图、合并组、自定义实体由 eng 起草、admin 发布；指标与标签由 an 起草、eng 发布。

### 2.2 十三个数据源

| 登记名 | 类型 | 表 | 业务 | 源端特点（映射要处理的） |
|---|---|---|---|---|
| `member_pg` | Postgres `fmcg_member` | members、memberships、points_ledger、redemptions、coupon_templates、coupons、consents、preferences | 会员中心（小程序会员） | 手机必有、unionid 约 80%；积分来源三种（订单、扫码、签到）；积分商城兑换单；短信、订阅消息两种同意 |
| `mall_pg` | Postgres `fmcg_mall` | orders、order_items、subscriptions | 小程序商城、鲜奶周期购 | **订单号从 1 起**（K1）；下单人是会员中心的会员号（跨源引用）；周期购卡 |
| `scan_mysql` | MySQL `fmcg_scan` | scan_users、scans、codes、sku_points | 一物一码平台 | 扫码 openid（与小程序不同）；成功 / 重复扫码 / 假码；测试批次 TEST；码的销售大区；SKU 的品牌与扫码积分（新品只在这里） |
| `station_mysql` | MySQL `fmcg_station` | members、bills、stations | 奶站订奶系统 | **账单号从 1 起**；手机带空格；**占位号 13800000000**（P04）；测试奶站 ST999；中文状态；每月 1 日北京时间 07:30 出账 |
| `erp_mysql` | MySQL `fmcg_erp` | products、regions | ERP 商品主数据、大区 | 60 个 SKU，8 个没填品牌 |
| `oms_mongo` | MongoDB `fmcg_oms` | orders | 订单中台 | 天猫、京东、抖音订单的第二份拷贝（中台上线后的），外加 B2B 团购单；售后退款只在这里；物流公司；约 2% 有旧版本文档；嵌套字段 |
| `tmall_s3` | S3 Parquet | buyers、trades、trade_items | 天猫旗舰店导出 | 只有 OUID；入会（会员通）约 30% 有明文手机；子订单商家编码约 5% 没填；Unix 毫秒；全量比对 |
| `jd_s3` | S3 CSV | jd_orders、jd_items、sku_map | 京东导出 | 用户 PIN；入会手机带 `86-`；明细只有京东 SKU，要用对照表换成商家编码 |
| `douyin_s3` | S3 CSV | dy_orders | 抖店导出 | 每单一行、买家内嵌；约 40% 授权明文手机；金额以分计；状态码数字；带货账号 |
| `events_s3` | S3 JSON | events | 小程序埋点 | user_id 是会员号（跨源引用）；匿名事件只有 device_id；签到 |
| `activity_s3` | S3 CSV | signups | 地推试饮报名表 | 手填手机格式杂、2% 错号；**导购代填自己的手机号**（P05）；是否领取试饮装 |
| `sellout_s3` | S3 CSV | ka_stores、sellout | 经销商回传的商超门店周销量 | 没有消费者；最近 26 周 |
| `wecom_duckdb` | DuckDB 文件（S3） | contacts、groups、group_members、mass_sends | 企业微信社群 | 外部联系人都有 unionid；进群、退群；群发 |

### 2.3 数据如何进入各层

```
13 个数据源 ──同步（水位线增量 / 全量比对，按表确认）──▶ 原始层 bronze_<数据源>.<表>（变更批次 _op/_batch/_commit_ts，文件加密）
           ──源视图（只读本数据源原始层的一条 SELECT）：拆买家、拆平台、换 SKU、清洗代填号、拆退群
           ──映射（字段表达式、值字典、where、dedupe、key_space、customer_source）──▶ 标准层 silver.<实体>（敏感字段加盐哈希）
                ├─ 合并组：order（取最新）、product（逐字段补齐）——同一主键只留一行
                ├─ silver._identities / _consumer_ids / _consumer_id_changes   身份打通与稳定的统一消费者 ID
                ├─ silver._consumer / _consumer_consent                        统一消费者的属性与同意
                └─ silver._device_owner                                         设备归属
           ──指标 / 标签（DSL）、分析模板（RFM、用户 360、同期群、复购、CLV、流失预警）──▶ 结果层 gold.*（每次一张快照）
           ──服务库（蓝绿切换）──▶ 点查接口 /api/v1/consumers/:id、目录接口 /api/v1/catalog
           ──工作台（只读 SQL、沙箱表）：扫码率、窜货、品类渗透
```

| 标准 / 自定义实体 | 来自（映射数） | 关键配置 |
|---|---|---|
| customer | member、scan_users、station members、tmall buyers、源视图 jd_buyers、源视图 dy_buyers、wecom contacts、源视图 signups_clean（8） | 默认身份规则；会员中心 `survivorship.priority: 1`；奶站 `nullif` 占位号；地推表在源视图里置空代填号 |
| order | mall（`key_space: mall`）、station bills（`key_space: station`、`where` 去掉 ST999）、tmall trades、jd_orders、dy_orders、源视图 oms_tmall / oms_jd / oms_douyin（8） | **合并组**：tmall、jd、douyin、三个中台视图，存活规则「取最新 updated_at」；中台视图各自 `customer_source` 指回自己的平台；B2B 单不在任何视图里 |
| order_item | mall（`key_space: mall`）、tmall trade_items、源视图 jd_lines、dy_orders（4） | 商品引用 ERP 的 SKU；天猫空商家编码 `nullif` |
| product | erp products、scan sku_points（2） | **合并组**：ERP 优先、逐字段补齐 |
| event | events、scans（`where` 去掉 TEST，值字典分成功 / 重复 / 假码）、redemptions（`where` 去掉取消的）、group_members、源视图 group_quits、signups（6） | 扫码的码号 `x_code` 登记了到 custom_code 的关系 |
| touch | mass_sends | 渠道 wechat |
| membership / points_transaction / coupon / coupon_template / consent / preference | member_pg（+ 奶站短信开关） | 积分原始来源留在 `x_reason` |
| 自定义维度 custom_region / custom_station / custom_code / custom_ka_store | ERP、奶站、扫码平台、商超 | 关系：`order.store_id → custom_station → custom_region`、`event.x_code → custom_code → custom_region`、`custom_ka_store → custom_region` |
| 自定义事实 custom_subscription | mall subscriptions | `customer_id` 登记了到 customer 的关系（跨源引用会员中心），能做指标的基础实体 |
| 自定义事实 custom_sellout | sellout | 复合主键 周 + 门店 + 商品；没有消费者，只能在工作台分析 |

共 42 个映射、8 个源视图、2 个合并组、6 个自定义实体、17 个指标、5 个标签。

## 3. 两档数据量

## 4. 探针与用例

时间都相对造数的 `--end`（数据终点日，UTC）；指标期望按 asOf = 数据终点日。完整的探针速查（pid、构造、每个指标的期望值）在 README 第四节。

### 身份打通（P）

| 用例 | 构造 | 正确结果 |
|---|---|---|
| P01 全渠道 | 会员（手机 + unionid）、扫码（unionid）、奶站（手机）、天猫入会（手机）、京东入会（手机）、抖音授权（手机）、企微（unionid） | 一个消费者；5 个下单渠道；营收 650；城市上海（第二轮改北京） |
| P02 扫码无身份 | 扫码用户没有 unionid、没有手机 | 单独一个（真实限制） |
| P03 扫码后绑手机 | 第一轮扫码用户只有 openid；第二轮领红包时绑了手机 | 第一轮两个，第二轮一个；会员那个 ID 留下，扫码那个记 `merge` 退役（ADR-0029） |
| P04 奶站占位号 | 267 位订奶户录了 13800000000（其中一人另有会员记录） | 映射 `nullif` 之后各自一个；**不去掉时 267 人并成一个**（实测，#254） |
| P05 导购代填 | 4 位导购各替 10 个路人填了自己的手机号，导购本人是会员 | 源视图置空代填号后，路人各自一个、导购仍是自己；不清洗时每位导购连着 10 个陌生人 |
| P06 匿名浏览后登录 | 设备匿名浏览 12 次后登录 | 设备归属到他，近 7 天浏览 12 |
| P07 天猫入会 / 未入会 | 入会的有明文手机，未入会的只有脱敏号 | 入会的并入会员；未入会的单独一个（脱敏号不能当手机号） |

### 主键与合并（K）

| 用例 | 构造 | 正确结果 |
|---|---|---|
| K1 编号独立 | 商城订单号、奶站账单号都从 1 开始 | 不写键空间：后合并的映射失败、列出冲突键；体检建议键空间；声明后订单数 = 两边之和 |
| K1b 引用忘了键空间 | 商城明细的 order_id 不写 `key_space` | 发布被拒，列出字段 |
| K2 重复接入 | 中台三个视图映射与三个平台的订单映射 | 不建组：中台映射合并失败（实测「共 32117 个」等）；体检建议建合并组；建组（取最新）后每个订单号一行，订单数 = 平台订单数 |
| K2a 中台退款更晚 | 平台「已完成」，中台 5 天后「已退款」 | 取中台：已退款，不计营收；物流公司来自中台 |
| K2b 平台确认收货更晚 | 中台「已发货」，京东 3 天后「已完成」 | 取京东：已完成；这一行没有物流公司（整行取较新的一边） |
| K3 商品补齐 | ERP 8 个 SKU 没品牌、3 个新品只在扫码平台 | 63 个商品；品牌全有（扫码平台补）；新品没有品类、标价 |
| K3b 换成按优先级 | 商品合并组改成 `priority` 发第 2 版 | 品牌缺 8 个（整行取 ERP）；对照 K3 理解两种规则 |
| K4 主数据引用 | 天猫子订单 5% 没填商家编码；京东明细经对照表 | 没填的明细商品为空，品类记「未关联」 |
| K5 同意冲突 | 会员中心同意短信（200 天前），奶站撤回（30 天前） | 统一消费者的短信同意 = revoked |
| K6 旧版本文档 | 中台约 2% 订单有旧版本（待付款） | 映射内去重后取最新的一版 |
| K7 行过滤 | 测试奶站 12 张账单、测试码 40 次扫码、B2B 团购单 | 都不进标准层；合并记录里有过滤行数 |
| K8 属性冲突 | 会员中心上海（300 天前）、奶站苏州（10 天前）、扫码杭州（5 天前） | 会员中心优先：上海；去掉优先级时是杭州 |

## 7. 新发现的缺口与建议

| issue | 现象 | 在哪一步看到 |
|---|---|---|
| #252 | 先合后拆以后，266 个退役 ID 的别名都指向留下原 ID 的那一个人，点查返回别人的结果 | T2.4（P04 先不去占位号再改正）、T9 |
| #253 ✅ | 源视图的 `view_key` 在同一批次里不唯一时任取一行，`dedupe` 失效：一位抖音买家的更新时间取成了旧单的，城市取舍跟着错。已修复：空跑与合并时报错，列出重复的标识，提示去掉 `view_key` | 造数时发现；crmlab 的抖音买家映射已改为不写 `view_key` |
| #254 | 占位号、代填号会把几百人并成一个，平台不提示 | T2.4、T2.6 |
| #255 | 指标做不了按商品品类的口径（订单明细不能做基础实体、过滤不能走到商品） | T5、T6 A3 |
| #256 | 点查只认统一消费者 ID，业务系统拿会员号查不到 | T9 |
| #257 | 独占冲突的报错没提键空间与合并组 | T3.1、T3.4 |

另外几点平台是有意这样设计的，但在快消场景里代价不小，建议讨论：
- **每天最多一张定时刷新的快照**（ADR-0028）。快消的扫码、订单一天内持续进来，「扫码未购」这类运营人群最好当天跟上。可以考虑按定义配置刷新间隔，或数据变化超过一定比例时同日再算。
- **合并组每个实体最多一个、组员键空间要相同**（ADR-0032）。本场景把三个平台和中台放进同一个组，是因为各平台订单号的长度不同、撞不上；真有撞号时只能给所有组员手写前缀表达式，引用字段也要跟着手写，失去发布时的一致性检查。
- **`customer_source` 对整列只能指一个数据源**（ADR-0030）。订单中台是快消最常见的数据入口，一张表混着几个平台，现在要拆成几个源视图、几个映射。可以考虑让 `customer_source` 由某一列的取值决定（如 `platform` 列 → 数据源名的对照）。
- **非消费者数据的分析**：商超销量只能进工作台。若要定期出「各大区扫码率」，需要非消费者粒度的指标或定时运行的工作台查询。
