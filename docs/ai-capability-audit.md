### 1.1 功能完整度

设计承诺（`docs/semantic-retrieval-design.md:5、:90、:101、:162-167`，第 8 节，ADR-0047、0049）与现状对照：

| 承诺 | 现状 | 依据 |
|---|---|---|
| 第一期不引入独立图数据库，关系展开是应用模块 | 符合：`expand.ts` 是纯函数 | `docs/semantic-retrieval-design.md:5、:101`；`app/.server/catalog/expand.ts:1-5` |
| 持久检索投影，按目录版本懒刷新，两类可见性 | 已实现：差异 ≤200 条在请求里同步刷新，否则入队 | `app/.server/catalog/projection.ts:22-31、:93、:162` |
| 多路召回 + RRF，别名优先 | 已实现：`LANE_WEIGHTS = { id: 4, alias: 3, name: 2, keyword: 1, vector: 1 }`，`RRF_K = 60` | `app/.server/catalog/rank.ts:14-19` |
| 作用域只加权不排除 | 已实现：page 与 conversation 两级「先留接口」，**没有接上** | `app/.server/catalog/rank.ts:19`，头注释 |
| 8.4「是否适合回答」二次排序（match / mismatch / unknown、draft_required）与可选的模型重排 | **未实现**：全仓搜不到 `draft_required`、`rerank` | grep `app/.server` 无结果 |

| 向量一路（可选），失败只去掉这一路 | 已实现。但租户开关 `hybrid_search` **默认关**，只有运营者能切换 | `app/.server/db/schema.ts:30、:42`；`embeddings.ts:122-134` |
| 设计 17 节：租户开关 `hybrid_search`、`analysis_planning` | 只有前者；`analysis_planning` 没有实现（计划校验对所有租户常开） | grep 无 `analysis_planning` |

### 1.2 准确度

- 确定性评测（本次在 `bf737cb` 上离线重跑）：调参集 32 条，Recall@20 95.3%；验收集 8 条 100%。`test/retrieval-golden.test.ts:13` 的下限 `BASELINE = 0.96` 按 40 条合计算。基线文档 `docs/test-plans/requirements-eval-baseline.md:16-32` 还停在 11-04 的数（93.8% / 85.7%），**文档过期**。
- 没召回全的条目（本次逐条算出）：
  - `churn-forecast`：Recall 0。「流失」没出现在任何说明里，属于知识缺失（`test/retrieval-golden.test.ts:16-19` 的 KNOWN_GAPS）。
  - `pv-7d-alias`：Recall 0.5。锚点投票时 event 实体不是锚点，依赖展开没补 `event.occurred_at`（同一处 KNOWN_GAPS）。连带的后果是起草 5 次都漏了 `event_type = view` 过滤（`requirements-eval-baseline.md:49`）。
- **黄金集与真实租户不一致**：fmcglab 上「消费金额」检索，前排都是原始字段和外键（`consent.customer_id` 等），`metric:revenue_365d` 排第 17；AI-PL1 原题排第 15（#1192，OPEN）。按 Recall@20 算这仍是「命中」，所以黄金集的口径看不出这个问题。设计要求另测 MRR / nDCG 和约束违背率（`semantic-retrieval-design.md` 第 14 节），**没有实现**。
- 黄金集 40 条，设计目标 100 条，另要中英文别名、跨租户同名、长目录压力集（第 14 节）。**未达规模**。
- 向量一路的收益**没有数据**：设计规定「比关键词基线有可证明的收益才默认启用」（`semantic-retrieval-design.md:626`），评测里的「开关对比」需要 embedding 才能跑，AI-R6 / AI-E3 都没做。

### 1.3 稳定性

- 投影不可用时回退到 `search()`（`projection.ts:5-6`），此时得分全为 0，一律按差异追问（ADR-0047），属于降级而非出错。
- **embedding 补算失败无声**：任务记为 succeeded；存储里一条向量都没有时，`vectorHits` 返回空结果，不报 fallback；每次检索都重新入队，再失败一次（#1172 OPEN，`embeddings.ts:121、:144-146`）。批大小问题已修（`ac8e7a2`，#1171）。
- 查询向量单独设了 3 秒短超时（`embeddings.ts:34`），失败只去掉这一路，设计合理。

**结论：部分达标。** 确定性层扎实。缺口是 8.4 二次排序、度量类说法的排序（#1192）、向量收益未证明、黄金集规模与指标口径。

## 2. 追问（需求不清时的澄清）

### 2.1 功能完整度

- 服务端判歧义：按名称或别名分组，逐维度对比度量、粒度、窗口、时间字段、过滤和口径声明；先做点名排除，再判定（`app/.server/catalog/ambiguity.ts:1-6、:122`）。`catalog_search` 输出 `ambiguous`、口径对比和追问（`app/.server/assistant/tools.ts:240-277`）。
- 词的默认指向（ADR-0056）已接进判定：`ambiguity.ts:5`，输出「默认口径：」行（`tools.ts:270-272`）。
- 未命中的词留候选组（⑥-5），点选后可以记为别名或默认指向提案（`app/.server/assistant/knowledge-ask.ts`）。
- 计划层：`clarify` 模式，以及口径声明未知或需复核时返回 `needs_clarification`（`app/.server/catalog/plan.ts:270-287`）。系统提示要求遇到 needs_clarification 先追问，本轮不再继续（`loop.ts:104`）。
- 起草页面遇到歧义**照常起草、只提示**（`app/.server/catalog/draft-search.ts:4`，#827 的决定）。这是有意取舍，但与助手的「先问清楚」不一致。

### 2.2 准确度

- 本次离线结果：调参集「追问正确率」87.5%，「应追问召回」55.6%（b 类 100%、c 类 50%、d 类 0%）；验收集都是 100%。
  - d 类的 0% 是**评测口径问题**，不是缺陷。`churn-forecast`、`hourly-orders`、`next-product-recommend` 标注了 clarify 文字，但它们属于平台做不到的需求，服务端歧义判定本来就不会对它们追问，应该由计划层给 `unsupported`。`retrieval.ts` 把它们算成「应追问」，分母因此偏大。
  - 真正的漏判是 `dormant-alias`（「找出沉睡客户」应追问而未追问）。
- 真实模型：AI-R3 第 1 轮正确追问了 revenue_365d 与 gmv_365d 的口径差异（#1178 的表格）；SK.13、SK.14 通过（`acceptance-plan.md` SK 行）。模型**是否照追问去问**没有量化，因为评测的计划模式一栏从未在真实模型上跑出数（见第 3 节）。

### 2.3 稳定性

- 判定是确定性的纯函数，不随模型变化。
- 观察（未开票，SK 行）：`catalog_search` 输出 10 条 324 行，口径对比在第 318 行，模型可能读不到；追问措辞有重复（「是是否扣除退款」）。

**结论：确定性层基本达标。** 不足有三：c 类漏判一条、评测把 d 类算进应追问、输出过长影响模型使用追问信息。

### 3.2 准确度

- **计划模式正确率从未记录过**：基线写「未上线」（`requirements-eval-baseline.md:10、:16-32`）。#423 只用假 LLM 跑通了流程；验收项 AI-E2 要求补上新基线，也没做（`acceptance-plan.md:1015`）。
- 已知错答：
  - AI-PL6「近一年**不含税**营收」：模型文字回答正确，计划却判 valid，并把含税 SQL 填进工作台（#1184 OPEN）。
  - AI-PL3、PL4：计划通过了，但 SQL 按单个数据源的 `customer_id` 归集，城市分布差 3%–5%，「100 个人」也不是 100 个人（#1183 OPEN）。校验层对 SQL 没有任何约束（见上表最后两行）。
  - AI-PL1：模型没走 `reuse_result`，因为目录里指标没有快照与粒度信息（#1182 OPEN；`app/.server/assistant/plan-card.ts:31-33` 对指标固定写「暂无快照」；目录只给模板条目写快照，见 `app/.server/catalog/index.ts:854`）。设计「优先复用已有结果」的意图落空。
- 评测本身的局限：`runPlanCase` 是**单次 JSON 输出**，把检索结果直接喂给模型（`scripts/eval-requirements/score.ts:219-247`）。它不走真实的工具循环，所以测不出 S6 暴露的那些工具编排问题。

### 3.3 稳定性

- 模型以前不知道计划长什么样，每轮失败 3–4 次、耗尽上限。已修：发送剥掉条件关键字的 `PLAN_SCHEMA`，并附最小示例（`f216046`，#1178；`tools.ts:280-287`）。修复后没有现场复测数据。
- 不走工具的 `callModel` 只发 `response_format: json_object`（`app/.server/llm.ts:365`），Schema 从来没发给模型。换成 inkling-2-mini 后，计划模式前 8 条**全部**因为 `request.dimensions` 不是数组被拒（#1191 OPEN）。评测的提示词也只写了「dimensions 必填」，没说是数组（`score.ts:191`）。
- 角色变化后，计划卡列出 6–8 行「语义哈希不一致」，容易误导（#1190 OPEN）。

**结论：部分达标。** 校验框架与硬性检查完整。口径检查覆盖面不足（#1184），SQL 与计划没有绑定，正确率没有真实模型数据。

## 4. 起草（「用模型生成草稿」）

### 4.1 功能完整度

- 指标：模型给出 spec 和逐项说明（items、unknowns、unsupported），转成 YAML；编辑框已有内容时先给只读草稿，点「确认覆盖」才替换（`5e0ff5a` #1162、`9e46fa7` #1163）。构建器里的「解析一句话」已删除，AI 起草统一走 YAML（`f766d89`，#1164；它以前会悄悄丢掉路径过滤和时间窗口，见 #1161）。
- 标签：支持多指标写法（`all` / `any`），有「做不到」出口，422 时显示模型给的原因（`2cc9a40`，#1165）。
- 工作台 SQL：有「做不到」出口（`aa6734c`、`4dedba0`，#1167）；目录只留最新快照，超长时按层裁剪（`1c54729`，#1174）。**口径假设（notes）还看不到**（#1187 OPEN）。
- 时间戳字段不能直接当维度，起草提示词已同步说明（`1d54f33`，#1166）。
- 流程：`modelDraftForDefinition` 只调用一次模型；Schema 或 DSL 校验不过就 422，**不让模型自修**（`app/.server/dsl-definitions.ts:198-241`）。这与助手里最多修正 3 次的做法不一致。

### 4.2 准确度

- 唯一的量化数据（`requirements-eval-baseline.md:42-49`）：qwen-plus 连跑 5 次，调参集校验通过 17/17，结构命中 95/96；验收集 2/2。失分的一例 `pv-7d-alias` 是检索问题。**这组数是 2026-11-04 在 `3fdf890` 上测的，早于 #1162 / #1165 改输出形状和提示词**，需要重测。
- 现场错答（已修）：AI-D2 只引用一个指标，买过的人也被打上「扫码未购」（#1165）；AI-D3 显示 Schema 报错，模型给的原因丢了（#1165）；SK.21 一句话解析在 qwen-plus 上必然失败（#959）。
- 评测脚本：标签输出 `{unsupported}` 时，`runCase` 按定义校验不过算失败（`score.ts:139-160`；#1165 的 Watch out 写明「本票不改」）。指标输出的 `unsupported` 也不进计分。所以「正确地说做不到」会被记成失败。

### 4.3 稳定性

- 模型差异：Schema 不发给模型（#1191）；可选键为 null（`922fda1`，#1160 已修）；平铺输出要宽松收拢（#959 已修）。
- 超时：`LLM_TIMEOUT_SECONDS` 默认 60 秒（`llm.ts:58-61`）；思考模型超时可以用 `chat_extra` 关掉思考（#952 已修，`60bde4f`）。

**结论：部分达标。** 功能面最近一周补得较全，但准确度数据过期，评测口径有偏，起草单次失败就不再自修。

### 5.2 准确度

- 2026-11-23 现场（fmcglab，qwen4-max，analyst，#1178 的表格）：6 轮里 5 轮工具调用到 13 次、撞上上限；每轮 `validate_plan` 失败 3–4 次；「按这个计划生成 SQL」也从 overview 重新开始。三处修复（#1178、#1179、#1180）都已合并，但**还没有修复后的现场复测**。
- AI-PL2：中途已经有两版 YAML 校验通过，第 4 次失败后超过 `MAX_FIXES`。交回给成员的是最后那版**不合法**的 YAML（#1185 OPEN）。原因是 `failures` 只在保存成功时清零（`loop.ts:202-204`），`unfixedReply` 用的是最后一次被拒的 YAML（`loop.ts:43-48`）。

### 5.3 稳定性

- **没有整轮的时间预算**：每次请求的超时是 60 秒，一轮可以有 13–15 次请求；现场每次失败的请求就要 15–25 秒（#1178）。inkling-2-mini 跑 AI-PL1 时一轮调了 20 次工具，同一查询重复 2–3 次，最后超时（#1192 的影响一节）。这里写的是 20 次，与 `MAX_TOOL_CALLS = 12` 不符；当时本地工作区把上限临时放宽到 30（#1179、#1189 的 Watch out），所以那次运行不是 main 上的配置。
- **中途一次模型错误就丢掉整轮**：`chatToolsWith` 抛出 `LlmError` 时直接 422（`loop.ts:180-184`），本轮已经通过的 plan 和 workbenchSql 都不返回。#1180 只处理了「撞上限」，没处理「中途出错」。
- 强依赖模型的工具调用能力：要先探测工具调用（`loop.ts:159`）；整轮固定一个路由（`loop.ts:157`，#531），这点是好的。

**结论：不达标，正在修复。** 三项结构性修复已合并（`f216046`、`d1e8770`、`193a93f`），但还没有复测数据。#1185、#1189、超时预算、中途出错这几个洞还在。

### 7.2 知识图谱（或加强 PG 关系展开）能解决多大比例

- **直接命中的只有 #5、#6，占 2/30 ≈ 7%。**
  - #5 是 `expand.ts` 锚点投票的局限：前 5 名里 order 与 consent 各两票，event 只有一票，成不了锚点（`test/retrieval-golden.test.ts:18`）。改投票规则或补「别名命中的字段所在实体」做锚点，就能解决，不需要图。

- **算上边缘情况，最多约 4/30 ≈ 13%**：
  - #1：如果用「指标 → 度量字段」的边给度量类说法加权，可以缓解。#1192 也指向了这个信号，但这在 `rank()` 里加一个特征就能做。
  - #7：「指标 → 快照 → 粒度」这类关系，加一行目录字段就能补上（#1182）。
- **图谱解决不了的占 85% 以上**：工具编排（20%）、结构化输出与模型差异、计划校验覆盖面、渲染与提示误导、UI。它们的根因分别在 Schema 怎么交给模型、loop 的预算与容错、校验规则、目录渲染，与关系存储的形态无关。
- **判断**：维持设计第 5 行「第一期不引入独立图数据库」的决定。优先在 PG 和应用层做三件事：
  1. 改进 `expand.ts` 的锚点规则，把指标的 depends_on 纳入自动展开；
  2. 把身份映射和快照粒度这类「隐性关系」补成目录条目；
  3. 在 `rank()` 里加度量信号。

  等黄金集扩到 100 条、并补上 MRR 与约束违背率之后，如果「关系没展开」类的占比明显上升（比如超过 20%），再重新评估。
