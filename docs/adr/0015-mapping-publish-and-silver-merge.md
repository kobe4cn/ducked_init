# 映射是平台解析的 YAML，双人发布后按变更批次合并进标准层：每个映射保存当前记录，受影响的去重键重新取最新

映射把数据源里的一张表对应到一个标准实体（或自定义实体），决定标准层里有什么。它既要让数据工程师（以及第 19 号切片里的大语言模型）方便地写，又不能成为一条把任意 SQL 带进运行时的通道（ADR-0003、0004）；既要支持去重与取最新，又要正确消费原始层的删除记录（ADR-0006）。

**文档。** 一个映射是一份 YAML：`model`（标准模型的大版本）、`entity`、`table`、`fields`（标准字段 → 表达式，或带值字典与兜底值的 `{ expr, dictionary, otherwise }`）、`extensions`（带类型的扩展字段；标准实体上以 `x_` 开头，避免与以后新增的标准字段重名；自定义实体以 `custom_` 开头，字段全写在这里）与 `dedupe`（去重键与取最新字段，不写时按实体主键去重）。保存与发布时先按 JSON Schema（`MAPPING_SCHEMA`，模型起草时也用它约束输出）校验结构，再对照标准模型与源表最近一次采集到的字段做语义校验；每个问题都给出 YAML 里的行列。不合格的文档不能保存为草稿。

**表达式是平台自己的小语言，不是 SQL。** 只有源表字段、字符串与数字字面量、`+ - * /`、括号和白名单函数（类型转换、日期时间解析、`from_timezone` 时区转换、Unix 时间、`coalesce`、`nullif`、大小写与去空白、`concat`、`substr`、`round`、`abs`）。平台解析成语法树后编译成 DuckDB SQL，字段一律加引号，字面量一律转义，所以写不出子查询、表函数或任何读文件、连库的调用。结果再转成标准字段的类型：时间一律是带时区的时间（不带时区的源端时间按 UTC 解读，北京时间等要用 `from_timezone` 声明），金额是两位小数的元。

**值字典。** 把源端取值的文本对应到标准枚举，目标只能是标准枚举里的值（扩展字段不限）。合并时遇到值字典里没有的取值、或者没有值字典的枚举字段遇到不是标准枚举的取值，默认这个映射合并失败，并列出出现最多的几个取值与行数，不悄悄写成空值。

字段（标准字段与扩展字段）可以声明**兜底值** `otherwise`：`null` 或一个标准枚举值（扩展字段不限），只能写在有值字典或标准枚举的字段上（否则无从判断哪些取值算没对应上），校验时与值字典的目标一样对照标准枚举。写了兜底值时，对应不上的取值写成兜底值，合并照常完成，合并记录里带上落入兜底的统计（每列共几种取值、共几行，出现最多的五个取值与各自的行数；行数按源表的行计，增量合并只统计本次变更的记录），映射详情页的合并记录据此显示。源端为空的取值仍为空，不算落入兜底。之所以要显式声明而不是默认兜底：常见取值只是样本里的前几名，源系统以后新加的状态也会出现，静默写成空值会让标准层悄悄变脏；声明了兜底值等于数据工程师认可这类取值归为一类，统计让他们看得到归进去了什么。统计里的原始取值写进任务结果，有 `sources:read` 权限的成员都能看到，与失败时错误信息里列出原始取值一致。兜底的告警留给第 22 号切片。

**双人发布与锁定。** 草稿由有 `sources:write` 权限的成员（管理员、数据工程师）保存，每个映射同时只有一份草稿；改过这份草稿的成员都记为作者（`authors`，用于审计），另记最后保存草稿的成员（`last_editor`）。发布需要 `publish` 权限，且发布者不能是最后保存草稿的人：每一处改动都要由另一个人看过才能发布（与 GitHub「有新推送时批准作废，最后推送者不能自己批准」一致）——B 改过 A 的草稿后由 A 发布，A 看到的是 B 的改动，A 原来的内容 B 改时已经看过。早先的规则是「发布者不能是作者之一」，两人互相改过草稿后谁都发布不了，草稿又丢不掉，会卡死。有 `sources:write` 权限的成员可以丢弃草稿（审计 `mapping.draft_discarded`），映射回到最近的已发布版本；从没发布过的映射整个删除，可以重新新建同一个「表 → 实体」映射。租户里只有当前成员有发布权限时，发布区提示先邀请一位数据工程师或管理员；是否允许单人租户自己发布另行决定。发布时对照数据源当前的字段再校验一次、同一实体上同名扩展字段的类型必须与已发布的映射（含本映射之前的版本）一致（标准层的列建好后不改类型），发布后版本锁定，再改就是新的一版草稿。表与实体在第一版定下，换表或换实体要新建映射；同一数据源的同一张表到同一个实体只有一个映射。被已发布映射引用的表不能移出同步范围（ADR-0013 当时预留的规则）。

**合并。** 任务 `silver.merge` 在工作进程里只挂载本租户的数据湖，参数是这次要合并的映射（见下面的触发）各自最新已发布版本的合并计划。标准层每个实体一张表 `silver."<实体>"`：实体的全部字段（没映射的为空）、扩展字段，加上 `_mapping`、`_source`、`_version`、`_merged_at`。不同映射、不同数据源写进同一张表，各自管理自己的行（按 `_mapping`）；把多个数据源里的同一个人合并成一个消费者是身份打通（第 11 号切片）的事。

每个映射在 `silver_records` 里保存**当前记录**：源表当前每条记录转换后的结果，带记录标识 `_src` 与最近的批次。源表的主键取自同步维护的当前主键状态（ADR-0012）：有主键时 `_src` 是主键的哈希，每个主键一行；没有主键时 `_src` 是整行哈希（与同步同一算法），每种整行一行并带出现次数。一次合并：
1. 读出原始层里上次合并之后的批次（原始层只追加，`_batch` 不超过本次上界的行不会再变，不必与同步互斥）。有主键时每个主键取这些批次里的最后一版（同一批次里一删一增取新增），最后一版是删除的移除；没有主键时按整行累计出现次数的变化，减到零的移除。
2. 转换新的版本，检查值字典与标准枚举之外的取值（没写兜底值时使这个映射失败，写了时记下统计）、去重键为空的行（使这个映射失败）。
3. 受影响的去重键 = 改动的记录在旧版本与新版本里的去重键。对它们在当前记录里重新取一行：取最新字段最大（空值最后），再按最近的批次，最后按记录标识，结果确定。所以源端的重复行只计一次，删掉最新的一行时标准层回落到剩下的那行，全部删掉时标准层的行也删掉。
4. 在一个 DuckLake 事务里改当前记录、删掉并重写这些去重键在标准层的行，并在合并日志 `silver._merges` 记下合并到了哪个批次。与 ADR-0012 的批次日志一样，它是下一次合并起点的唯一依据。

首次合并、映射换了版本、或源表的主键变了（成员改了业务主键）时，由原始层的全部批次重建这个映射的当前记录与标准层的行。每个映射各自一个事务，一个映射失败不影响其他映射；源表还没同步进原始层的映射跳过，不算失败。

**触发与范围。** 合并任务只带这次需要合并的映射，没带上的映射不记合并记录，合并记录里看得出哪次合并真正动了哪个映射：
- 发布后：只带刚发布的映射，立即入队。
- 同步任务结束（含部分失败）后：只带这次同步给源表写入了变更的已发布映射（同一数据源、同一张表、本批次写入原始层的行数大于 0），与映射无关的数据源、没有变更的同步都不触发。
- 常驻调度器定期检查，按映射判断是否到期：映射已发布、租户未停用，带它的最近一次合并不在排队，且 (a) 这次合并带的不是它最新的已发布版本（还没合并过也算），或 (b) 这次合并开始之后，有同步按同一判断给它的源表写入了变更。同一租户的合并一个接一个，入队与补映射都在租户锁里取最新版本，所以最近一次带它的合并带的就是合并过的最高版本，检查只需找这一次，不随历史合并增多而变慢。到期的映射按租户合成一个合并。(a) 按版本号而不按发布时间判断：发布时间是事务开始时间，可能早于并发领取的合并的开始时间。(b) 看带这个映射的合并而不看租户最近一次合并：同步结束与同步后的入队是两个事务，中间可能有不带这个映射的合并被领取。合并失败也算带过这个版本，不自动重试（失败多半要改映射或源数据，重试只会重复失败）；源表再写入变更或发布新版本时再合并。
- 成员在映射列表手动「立即合并」：带全部已发布映射，没有新批次的映射照常记一条合并记录，显示为“无新批次”；已有合并在排队时把全部映射补进去，在运行时提示稍后再试。
- 成员在已发布映射的详情页「立即合并」：只带这个映射（最新已发布版本）；已有合并在排队时把它补进去，在运行时提示：它结束后，这个映射还有没合并的版本或变更时由定时检查补上（运行中的合并已带着它的最新版本、之后也没有变更时不再补）。

同一租户同时只有一个合并在排队或运行（两个合并同时写同一张标准层表会冲突）：入队前锁住租户行再检查。已有合并在排队时，新的需求把映射补进那个合并（按映射去重，同一映射换成最新版本），成员马上看得到；领取合并不锁租户行，所以只用“仍在排队”为条件改它的参数，刚被领取或已在运行时不补，由定时检查在它之后补上。每个映射实际合并到哪个批次以 `silver._merges` 为准，晚一次合并只会推迟，不会漏掉批次。映射页的合并状态只看带这个映射的合并任务，并按这个映射自己的结果判断成败，别的映射合并失败不显示在这里。

## 已接受的取舍

- 敏感信息（标准模型里标为敏感的姓名、手机号、邮箱）在转换这一步换成按租户加盐的哈希，哈希上线前按明文合并的标准层在下次合并时重建（细节见 ADR-0005）；原始层加密仍待补上。
- 发布前没有样本空跑与新旧版本差异（第 9 号切片），校验只覆盖结构、字段是否存在与值字典的目标；表达式在真实数据上出错（如转换失败）要到合并时才发现，此时这个映射合并失败、标准层保留上一次的结果。
- 当前记录多存一份转换后的源表（有主键的表每个主键一行），标准层表另存去重后的结果。换来的是增量合并只碰受影响的去重键，删除与重复行都能正确回落。
- 重建与大批次的合并没有像同步那样按哈希分桶（ADR-0010），超出内存时靠 DuckDB 溢写到任务临时目录；超大表的首次合并可能需要提高租户配额。
- 记录标识与整行哈希是 64 位哈希，与同步一样接受碰撞的极小概率。
- 合并任务的参数在领取前可以补映射，领取后取定：运行期间又发布的版本、又写入的变更由定时检查在它之后再合并一次，最多晚一个检查周期。
- 漂移检查报告缺列时，成员可以在数据地图上重建合并这张表：写入它的已发布映射都带强制重建标记入队一次合并，走与换版本相同的全量重建路径，建表那一步补上缺的列。强制重建只补列，不改列类型、不删列：类型不一致要删表重建（另行设计），多列与孤表不影响合并，平台不删除湖表。已有合并在排队或运行中时不入队；排队中的映射带了重建标记时，之后补进来的同一映射保留它。

## Considered Options

- 映射里直接写 SQL 片段（或 dbt 模型）：表达力最强，但模型生成的 SQL 无法被机器可靠地校验，也无法阻止读文件、连外部库，违背 ADR-0003、0004。否决；复杂情况走人写、人发布的源视图（第 9 号切片）。
- 每次合并把整个映射从原始层全量重算：实现最简单，但开销随原始层历史增长，与小时级同步不匹配。只在首次、换版本或主键变化时这样做。
- 不保存当前记录，靠原始层历史找出删除记录对应的旧去重键：删除记录只带主键，要回溯历史才能知道它原来属于哪个去重键，且去重时还要知道同一去重键下其余仍存在的记录，等于每次都要把历史重放一遍。不采用。
- 合并与同步放在同一个任务里：少一次派发，但同步的每张表、合并的每个映射失败的语义纠缠在一起，发布映射后也要等下一次同步才能看到标准层。不采用。
