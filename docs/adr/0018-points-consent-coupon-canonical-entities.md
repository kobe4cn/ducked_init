# 积分流水、营销同意、兴趣偏好、优惠券、券模板升格为标准实体；同一大版本内新增实体算兼容，小版本随新增内容加一

标准模型现在只有 7 个实体：消费者、订单、订单明细、商品、行为事件、营销触达、会员。积分、同意、优惠券几乎每个 CRM 租户都有，但没有标准实体，只能写成自定义实体（`custom_` 开头，ADR-0015）。这样平台的模板指标与标签用不上它们，每个租户都要自己再定义一遍；`membership.points` 只是当前余额，算不出积分获取与消耗、兑换率、过期率。`canonical-model.ts` 头部写的兼容规则是「同一大版本内只新增字段」，没说新增实体算不算兼容。

现在决定：

**新增五个标准实体。** 字段类型只有 `string`/`integer`/`decimal`/`timestamp`/`date`/`boolean`（`FIELD_TYPES`）；主键（`key`）是映射没写 `dedupe` 时的去重键：这时主键的每个字段都必须映射，且合并时不能为空（ADR-0015：去重键有空值整个映射失败）。主键都选源端一定有、或能由源表主键拼出来的列。五个实体都没有字段标 `pii`，与现有实体一致（`customer_id`、会员号都不标）。

1. **`points_transaction` 积分流水**：一笔积分变动。主键 `points_transaction_id`。

   | 字段 | 类型 | 中文名 | 说明 |
   |---|---|---|---|
   | `points_transaction_id` | string | 流水 ID | 源端的积分流水标识；源端没有时可用字段拼出 |
   | `customer_id` | string | 消费者 ID | 积分所属的消费者，对应消费者的 customer_id |
   | `membership_id` | string | 会员号 | 积分所属的会员，对应会员的 membership_id |
   | `change_type` | string | 变动类型 | 枚举 `earn`（获得）、`spend`（消费抵扣）、`redeem`（兑换礼品或权益）、`expire`（过期）、`adjust`（人工调整、退款冲回等） |
   | `points_change` | integer | 变动积分 | 带正负：增加为正，减少为负 |
   | `balance_after` | integer | 变动后余额 | 这笔变动之后的积分余额，源端没有为空 |
   | `order_id` | string | 关联订单 | 产生或使用这笔积分的订单，对应订单的 order_id |
   | `occurred_at` | timestamp | 发生时间 | 积分变动的时间 |
   | `expires_at` | timestamp | 到期时间 | 这笔获得的积分的到期时间，不过期或不是获得为空 |

   - 变动量叫 `points_change` 而不是 `points`，避免和 `membership.points`（余额）同名不同义。
   - 与 `membership.points` 的边界：`membership.points` 仍是源端给出的当前余额，积分流水是变动历史。平台不用流水推算余额，也不拿余额校对流水（源端可能清理过早期流水，同步范围也可能只有一部分）。看余额用 `membership.points`，看获取、消耗、兑换、过期用积分流水。
   - 兑换礼品**不单独成实体**：兑换在流水里是 `change_type = redeem` 的一笔，兑换率、兑换消耗的积分都能由流水算出。兑换单、礼品目录各租户差别大，需要时先走自定义实体（#44），以后要升格也只是再新增实体。

2. **`consent` 营销同意**：消费者在某个渠道上是否同意接收营销信息的**当前状态**。只管营销同意，隐私协议、用户协议的签署不在这里。主键 `customer_id` + `channel`。

   | 字段 | 类型 | 中文名 | 说明 |
   |---|---|---|---|
   | `customer_id` | string | 消费者 ID | 对应消费者的 customer_id |
   | `channel` | string | 渠道 | 枚举与 `touch.channel` 共用一套：`sms`、`email`、`push`、`wechat`、`app`、`other` |
   | `status` | string | 同意状态 | 枚举 `granted`（同意）、`revoked`（撤回或拒绝） |
   | `granted_at` | timestamp | 同意时间 | 最近一次同意的时间 |
   | `revoked_at` | timestamp | 撤回时间 | 最近一次撤回的时间，没撤回过为空 |
   | `updated_at` | timestamp | 更新时间 | 源端最后一次修改这条记录的时间 |

   - 渠道枚举与 `touch.channel` **共用一套**：实现时提成一个常量，两个字段都引用它。这样触达可以直接对照同意（「向撤回了短信同意的人发了短信」）；以后要加渠道（如电话外呼）两边一起加。
   - 状态用字符串枚举而不是布尔：按规则生成草稿只在源列类型是 BOOL 时才自动对应布尔，MySQL 的 `TINYINT(1)`、`'Y'/'N'` 这类写法用值字典对应到 `granted`/`revoked` 更稳；以后要区分「从未表态」也只需加一个枚举取值。
   - 源端是同意变更日志（每次同意或撤回一行）时，把日志的发生时间映射到 `updated_at`，映射在 `dedupe` 里声明 `latest: updated_at`，合并按「同一消费者、同一渠道取最新」得到当前状态。

3. **`preference` 兴趣偏好**：消费者的一条偏好（键值）。主键 `customer_id` + `preference_type` + `preference_value`。

   | 字段 | 类型 | 中文名 | 说明 |
   |---|---|---|---|
   | `customer_id` | string | 消费者 ID | 对应消费者的 customer_id |
   | `preference_type` | string | 偏好类型 | 如 `category`（品类）、`brand`（品牌）、`flavor`（口味）、`size`（尺码）；不设标准枚举 |
   | `preference_value` | string | 偏好值 | 偏好的取值（如某个品类名、品牌名） |
   | `updated_at` | timestamp | 更新时间 | 源端最后一次修改这条记录的时间 |

   - 同意与偏好**分成两个实体**：同意是「渠道 × 状态」且有合规含义，主键是消费者 + 渠道；偏好是开放的键值，一个消费者在同一类型下可以有多个值。放在一起要么主键说不清，要么同意的状态和时间字段在偏好行上全是空的。
   - `preference_type` 不设标准枚举，与 `event.event_type` 一样只在说明里给常用写法：偏好的类型随行业变化大，强行枚举只会让大量取值落到 `other`。
   - 只放源端记录的偏好（消费者自己填的、源系统算好的）。平台根据行为推断的偏好是标签，不写回这里。过敏、孕期等健康信息不放进偏好，要放走自定义实体并标敏感（等 #44 与 ADR-0005 落地）。

4. **`coupon` 优惠券**：发给消费者的一张券。主键 `coupon_id`。

   | 字段 | 类型 | 中文名 | 说明 |
   |---|---|---|---|
   | `coupon_id` | string | 券 ID | 源端的券实例标识或券码 |
   | `coupon_template_id` | string | 券模板 ID | 这张券的模板，对应券模板的 coupon_template_id |
   | `campaign_id` | string | 活动 ID | 发券的营销活动，与营销触达的 campaign_id 同义 |
   | `customer_id` | string | 消费者 ID | 领到这张券的消费者 |
   | `status` | string | 券状态 | 枚举 `issued`（已发放、未使用）、`redeemed`（已核销）、`expired`（已过期）、`voided`（已作废） |
   | `issued_at` | timestamp | 发放时间 | 券发到消费者手里的时间 |
   | `redeemed_at` | timestamp | 核销时间 | 券被使用的时间，未核销为空 |
   | `order_id` | string | 核销订单 | 使用这张券的订单，对应订单的 order_id |
   | `discount_amount` | decimal | 抵扣金额 | 核销时实际抵扣的金额（元），未核销为空 |
   | `expires_at` | timestamp | 到期时间 | 这张券的到期时间 |
   | `updated_at` | timestamp | 更新时间 | 源端最后一次修改这条记录的时间 |

5. **`coupon_template` 券模板**：券的定义。主键 `coupon_template_id`。

   | 字段 | 类型 | 中文名 | 说明 |
   |---|---|---|---|
   | `coupon_template_id` | string | 券模板 ID | 源端的券模板或券批次标识 |
   | `name` | string | 券名称 | 券的名称 |
   | `coupon_type` | string | 券类型 | 枚举 `cash`（代金、满减）、`discount`（折扣）、`gift`（赠品、兑换）、`shipping`（免运费）、`other` |
   | `face_value` | decimal | 面额 | 代金券、满减券的面额（元），其他类型为空 |
   | `pay_percent` | decimal | 应付比例 | 折扣券打折后应付的百分比（85 折写 `85`、87.5 折写 `87.5`），其他类型为空 |
   | `min_spend` | decimal | 使用门槛 | 满多少元可用，无门槛为空 |

   - 主键按 `<实体名>_id` 的习惯叫 `coupon_template_id`；`pay_percent` 记应付比例而不是减掉的比例，与「85 折」的说法一致。
   - 券模板**单独成实体**，与订单明细和商品的分法一样：源端的券表大多只存模板 ID，面额、类型在模板表里；一个映射只对应一张表，模板字段放在券上就填不上。券上只留实例自己的事实（核销时实际抵扣了多少）。

**兼容规则。** 同一大版本内只做新增：新增实体、给已有实体新增字段、给标准枚举新增取值，都算兼容；已有实体与字段不改名、不改语义、不改类型，已有实体不改主键。新增的东西不影响已发布的映射：映射里的 `model` 只写大版本，旧映射照样通过校验与合并。新实体的名称不以 `custom_` 开头，与自定义实体不会重名。

**版本号。** `MODEL_MAJOR` 保持 1。`MODEL_VERSION` 的小版本标记标准模型的内容：每次新增内容（实体、字段或枚举取值）加一，在新增内容的同一次改动里改，并同步改 `test/http/mappings.test.ts` 里对「标准模型 v1.x」的断言。本 ADR 只是决定，不改版本号；三张实体票（#48 积分流水、#49 营销同意与兴趣偏好、#50 优惠券与券模板）落地时各加一次。

**已用自定义实体承载这些数据的租户怎么迁。** 平台不自动搬数据，也不改写旧映射：
1. 对同一张源表新建一个映射，实体选新的标准实体，从按规则生成的草稿开始（ADR-0017）。映射的实体在第一版定下，不能把旧映射改成新实体；同一张表到不同实体可以各有一个映射。
2. 旧映射 `extensions` 里的字段（不带 `x_` 前缀）逐个对照：能对上标准字段的写到 `fields`，类型按标准模型转换；对不上的写成扩展字段，名称加 `x_` 前缀，类型与旧映射保持一致。
3. 双人发布后首次合并由原始层的全部批次重建（ADR-0015），新标准层表 `silver."<新实体>"` 拿到完整历史，不需要旧表 `silver."custom_x"` 里的数据。
4. 旧映射暂时留着：平台还没有停用映射的功能，`silver."custom_x"` 会继续被合并，但模板指标与标签只读标准实体，不受影响。停用映射做出来之后再下线旧映射并删掉旧表。

**与 #44 的关系。** 本 ADR 只管升格这五个实体，#44（自定义实体登记、指标与标签能引用什么）另写 ADR。本 ADR 让 #44 的范围变小：积分流水、营销同意、兴趣偏好、优惠券、券模板以后不再需要自定义实体；兑换单、礼品目录、健康类偏好和租户特有的业务表仍是自定义实体。

## 已接受的取舍

- `points_change` 带正负。源端只存绝对值、另有方向列时，表达式里没有条件判断，写不出取负；要等源视图（还没做）或以后给表达式加条件函数。合并不检查符号是否和 `change_type` 一致。
- `consent` 按「一行一个渠道」建模。源端是宽表（一个消费者一行，`sms_opt_in`、`email_opt_in` 各一列）时，一张表到一个实体只能有一个映射，只能映射其中一个渠道，其余要等源视图把宽表拆成行；全渠道退订的开关同理。在那之前，这类数据可以先作为扩展字段挂在 `customer` 上。
- 同意与偏好的主键都包含 `customer_id`，去重按映射各管各的（ADR-0015），两个数据源对同一个人的同意各占一行，合成一个人的结论要等身份打通。
- `pay_percent` 是两位小数，更细的折扣会被舍入；`preference_type` 没有标准枚举，模板指标按偏好类型分组前要看各租户实际写了什么。
- 小版本随每次新增加一，三张实体票落地后会是 1.3 而不是 1.1；换来的是版本号和标准模型页上看到的内容始终一致。

## Considered Options

- 兑换单、兑换商品一并升格：能算到礼品粒度，但礼品目录各租户差异大，现在定字段多半要改；兑换率与兑换消耗的积分靠流水已经能算。暂不升格，以后升格也是兼容的新增。
- 同意与偏好合成一个「偏好与同意」实体（类型 + 键 + 值）：实体少一个，但同意的渠道枚举、状态与时间在偏好行上都没有意义，主键也只能退化成拼接字符串。否决。
- 同意的渠道单设一套枚举（含电话、全渠道）：贴合同意的说法，但触达与同意对不上号，合规检查要再写一层对照。否决；缺的渠道两边一起加。
- 同意状态用布尔：最直观，但草稿只认 BOOL 列，常见的 `TINYINT(1)`、`'Y'/'N'` 都要手写转换，也没法再加第三种状态。否决。
- 券模板的面额、类型直接放在券上：少一个实体，但多数源端的券表没有这些列，且一个映射只能读一张表，结果多半是空的。否决。
- 新增实体就升大版本：最保守，但现在升大版本会让所有已发布映射校验不过，也没有迁移工具（`issue_need_follow.md`）。新增实体不影响旧映射，不需要升大版本。
- 三张实体票共用一次 1.1：版本号好看，但中间状态（只加了积分流水）和最终状态都叫 1.1，版本号就不能说明模型里有什么。否决。
