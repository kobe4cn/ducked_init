# 源表结构指纹：同步时记在湖里，与上一次记下的结构比对

源端改表结构（删列、改类型）以前只有两处能看出来：核对湖中数据（ADR-0014）时与原始层对照，和映射的列差异检查（重新采集后）。同步本身照常进行，成员不知道哪一次同步起源表变了，合并也没有依据去判断这次变化会不会写坏标准层（#158）。

**每次同步记一份结构指纹。** `syncTable` 读源表时本来就要 `DESCRIBE` 一次（水位线字段的类型、整行哈希的列），用这份列名与类型作为本批次的源表结构指纹（CONTEXT「结构指纹」），存进湖里新表 `bronze_<id>._schemas`（`table_name`、`batch`、`columns` JSON `[{name,type}]`、`changed` JSON）。它与变更批次、`_batches` 在同一个 DuckLake 事务里写入：批次与结构要么一起提交、要么都不提交，不会出现批次写了、结构还是旧的。结构没变也写一行（`changed` 为 `{changed:false,…}`），后续读取方直接取这张表 `batch` 最大的一行即可。主键比对批次（`reconcile`）不重读整表结构，不记。老湖靠 `CREATE TABLE IF NOT EXISTS` 补表，不改 `_batches` 的列。

**存在湖里，不存平台库。** 同步与合并在工作进程里跑，工作进程不连平台库，任务需要的平台数据都由入队时放进参数（ADR-0014 的漂移检查同样如此）；合并判断结构变化（#208）时只能读湖。与 `_batches` 作为水位线的唯一依据同理（ADR-0012）：任务结果没记下来，湖里的结构也与实际写入的批次一致。

**基线是上一次记下的源表结构，不是原始层的列。** 原始层只加列、不删列（ADR-0014：湖中多出的列是源端删除字段后保留旧列的预期结果），拿它当基线，历史上删过的列会在之后每一次同步里都报成「删除」。所以比的是上一次同步时源端的样子，每次变化只报一次。

**判定规则。** `diffColumns(prev, next)`（`schema-diff.ts`）按列名比较：新增（next 有、prev 没有）、删除（prev 有、next 没有）、改类型（两边都有、类型不同，带原类型、新类型与 `widened`）。只是列的顺序变了不算变化。`widened` 用 `isWidened(from, to)`：已有的值都能无损地放进新类型（整数加宽、FLOAT → DOUBLE、DATE → TIMESTAMP、DECIMAL 位数够、任何类型改成 VARCHAR）。核对湖中数据的结构项（ADR-0014）共用同一个函数，以原始层为 prev、源端为 next。某张表第一次记结构时没有上一版：只存（`changed` 列为 NULL），同步记录里 `schema.changed` 为 false。老湖升级后每张表的第一次同步同样算第一次。

**破坏性变化**：删除列；或改类型且不是放宽；或改成 VARCHAR（`isWidened` 把它算作放宽，但原来的数值、日期列变成文本，映射里的表达式与标准层的类型都会受影响）。新增列不算破坏性。`isBreaking(from, to)` 判断改类型这一半。

**合并前检查（#208）。** `mergeMapping` 在读输入之后、任何写入之前，取这张表在 `_schemas` 里 `batch` 最大的一行，用 `breakingColumns` 对照映射引用的源列（`referencedSourceColumns`：列表达式与 `where`，源表列差异也用它）：引用的列不在最新结构里，或 `isBreaking(原始层类型, 最新类型)`，这个映射就合并失败，报错「映射引用的源列 phone 已被删除：…」（列名在第一个全角冒号前，快照「数据不完整」的摘要只留这一段）。原类型取原始层表里这一列的类型而不是上一次的结构：原始层类型从建表起不变（ADR-0014），所以源端没恢复时之后每次合并都持续失败，直到映射改版不再引用它或源端恢复，不会因为只比相邻两次而只失败一次、随后把空值悄悄写进标准层。失败只记在本映射（ADR-0015 的失败隔离），标准层保留上一次的结果，同实体后续映射与其他实体照常合并。没有 `_schemas` 或这张表还没记过结构（老湖还没同步过）时跳过；源视图的映射跳过（引用的是视图的输出列）。

**没有行变化也要合并。** 删列或改类型不一定让同步写入行（例如 int 改成 text，取值的文本表示不变）。`syncWroteMappingTable` 把同步记录里这张表 `schema.removed` 或 `schema.typeChanged` 非空也算作写了映射的表，同步后照常入队合并，让上面的检查报出来。

**通知（#208）。** `source.sync` 任务结束后调度器调用 `alertSchemaBreak`（`schema-alerts.ts`）：同步记录里各表的删除列与 `isBreaking` 的改类型（这里只有相邻两次的结构，原类型取上一次的）与这个数据源已发布、未停用、读源表的映射引用的列求交，有交集时记一条平台审计（`source.schema_broken`，只写映射、表与列名），并给有 `sources:write` 的成员各发一封邮件。结构没变的同步不发，所以同一次变化只通知一次；合并持续失败由映射的合并记录与快照的「数据不完整」体现。

**展示。** 同步记录（`source.sync` 任务结果）成功的批次带 `schema`，数据源页的同步历史在结构有变化的批次下面加一行，列出删除与改类型的列（红色、带图标）和新增的列；失败的记录不带结构。

## 已接受的取舍

- 结构只看列名与 DuckDB 类型，不看可空、默认值、注释：这些不改变读进湖里的值。
- 列改名表现为一删一增，不尝试识别改名。
- 同一次同步里有水位线、没有主键的表到了比对周期会紧接着再全量比对一次，那个批次也记一行结构，与前一个批次相同，不算变化。
- 告警只看相邻两次的结构（平台进程不读湖），合并检查对照原始层类型，两者可能不一致：源端把改坏的类型改回原始层的类型时，告警仍会按「改类型」发一封，而合并已能通过；连续多次改类型时以合并记录为准。
- 只有同步时才记结构：源端改了结构、还没同步时看不到，需要时由核对湖中数据实时对照。
