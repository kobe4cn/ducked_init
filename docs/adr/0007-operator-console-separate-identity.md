# 运营后台使用独立于成员的运营者身份，只管理租户元数据

租户开通、管理员恢复、配额、默认模型服务等工作需要一个网页后台。之前的默认做法是只提供运营命令，现在改为同时提供运营后台。不在成员体系里加一个跨租户的“超级管理员”角色，原因是：成员会话遍布各租户的日常使用，一旦某个会话泄露或权限检查漏写一处，跨租户角色就会让所有租户同时暴露，破坏 ADR-0001 的隔离前提。

因此运营者是一套独立的身份：
- 独立的表：`operators`。
- 独立的登录入口：`/ops/login`。登录用 Magic Link，之后必须再通过 TOTP。
- 独立的会话与 cookie：会话有效期较短。
- 独立的路由前缀：`/ops`。

运营者只能管理租户的元数据，包括开通、改名、指定管理员、停用与恢复，以及后续切片里的配额、退出和默认模型服务。对租户成员，运营者只看得到成员数和管理员邮箱。运营者看不到任何租户的业务数据，也不能以成员身份进入租户。

运营者只能在服务器上用运营命令创建。服务器访问权限是信任的根。运营者之间不能互相管理：后台既不能新增运营者，也不能停用运营者。运营命令保留，与后台调用同一套领域函数。

运营者对租户的每一次操作都写入该租户的审计日志，操作者一栏标明“运营者”及其邮箱，租户管理员可以看到。与租户无关的平台级事件记在同一张表中，租户字段为空，只在运营后台可见。这类事件包括运营者登录、新增运营者等。

## Considered Options

- 在成员角色中增加“超级管理员”：实现最省，但同一个会话能跨越所有租户，一处漏检就会全面泄露。否决。
- 只提供运营命令、不做后台：攻击面最小，但日常运营（尤其是恢复管理员）需要登录服务器，不便于交给非工程人员。否决，命令作为底层入口保留。
- 运营后台单独部署（独立进程或域名）：隔离更强，但本期部署复杂度过高。保留为后续加固选项：路由集中在 `/ops` 前缀下，便于将来拆出。
