# 指标与标签用平台自有 YAML DSL 与分析模板，不用 dbt

仓库里已有 dbt 项目，但租户数以百计时，每个租户维护一个 dbt 项目的运维与隔离成本过高，dbt 的自由 SQL 也难以让大语言模型草稿被机器校验。决定：平台自定义一套小型 YAML DSL（度量、维度、过滤、时间窗口），外加参数化的分析模板，由确定性编译器生成 DuckDB SQL，交给平台自己的任务调度执行。现有 `src/` 与 `dbt/` 中的 SQL 作为首批模板的实现来源。

分析模板是通用登记的：注册表 `TEMPLATES` 里每个模板给出参数校验、编译函数、读到的实体与计算前必须有的标准层表，`TASK_KINDS` 给出运行它的任务类型 `gold.<模板 ID>`；任务、快照登记与断言失败告警都按注册表通用处理，加一个模板只需新建模板文件并在这两处各加一行。模板 ID（即种类名）以小写字母开头、只含小写字母与数字，快照表名 `gold."<模板 ID>__<任务 ID>"` 的校验（快照过期、服务库）是 `[a-z][a-z0-9]*__`。按订单计算的模板共用一份订单口径（`order-window.ts` 的 `qualifyingOrders`：状态计入、不晚于 `asOf`，给了回看天数时只取窗口内的，交易时间取 `coalesce(paid_at, created_at)` 的 UTC 日期，带打通到的统一消费者）。RFM 之后的模板（用户 360 `user360`：每个统一消费者一行订单汇总与各渠道同意；同期群 `cohort`：首单在最近若干个月或周里的消费者各一行首单周期、单数与有下单的周期偏移，首单取全部历史；复购 `repurchase`：回看窗口内下过单的消费者各一行首单、第二单与是否在复购窗口内复购）都是每个消费者一行，交给页面再聚合，不进服务库，服务库仍只收 RFM 与指标、标签（ADR-0033）。

## Considered Options

- 每个租户生成一个 dbt 项目：否决，理由如上。
- dbt Semantic Layer / MetricFlow 规范：表达力强，但引入外部规范与工具链依赖，且与自有的模板参数体系不契合，否决。
