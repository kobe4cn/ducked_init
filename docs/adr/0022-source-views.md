# 源视图是只读本数据源原始层的一条 SELECT，保存时用 DuckDB 解析器限定引用的表，按映射的规则由人双人发布

映射一次只读一张源表（ADR-0015）。有的源表要先整理才能映射：拆宽表、连接码表、按状态挑行。#95 让数据工程师在某个数据源下编写源视图，作为映射的输入（#96 再让映射读它）。源视图是成员手写的 SQL，直接在租户的数据湖上执行，所以先要定清楚它能读什么、能不能写、谁能让它生效。

**一个数据源下的一条 SELECT。** 源视图存在 `source_views`（`(source_id, name)` 唯一，名字是小写标识符，映射里像表名一样引用它），SQL 存在它的版本 `source_view_versions`（`sql`）里。表名直接写源表名，也可以带上本数据源原始层的 schema 前缀，但不能带 catalog。

**写入由只读挂载挡住，跨 schema 读取另由解析器挡住。** 校验与预览都在请求内用 `openTenantLake(..., { readOnly: true })` 挂载数据湖（同映射空跑），任何写入都会被 DuckDB 拒绝。只读挂载挡不住读别的 schema，所以执行前先用 DuckDB 自己的解析器 `json_serialize_sql` 拿到解析树（`pipeline/source-view-engine.ts` 的 `checkViewSql`）：
- 只能有一条语句，而且必须是 SELECT。`json_serialize_sql` 对 SELECT 以外的语句直接报错。
- 解析树里每个表引用（含子查询、表达式里的子查询、CTE 里的查询）都检查一遍。基表不能带 catalog；schema 只能为空或本数据源的 `bronze_<数据源 ID>`。不带 schema 的表名要么是所在作用域里的 CTE（一个查询定义的 CTE 只在这个查询里可见，外层同名的引用不算），要么是本数据源原始层现有的表。这样 `silver`、`gold`、其他数据源的原始层、本数据源的 `_keys` / `_mirror`、会话的本机库 `stage`、DuckDB 的系统视图都读不到。
- 能读出会话配置或环境的标量函数（`getenv`、`current_setting`、`getvariable`）拒绝。
- 表引用的种类按白名单放行：基表、子查询、连接、`VALUES`、`PIVOT`。表函数（`read_parquet` 等可以读任意路径）和 `SHOW` / `DESCRIBE` / `SUMMARIZE` 一律拒绝。以后 DuckDB 新增的种类也默认拒绝。

我们没有自己写 SQL 解析器，也没有用正则匹配表名。DuckDB 的解析器就是执行时用的那一个，引号、注释、大小写的处理和执行完全一致。

**视图必须输出平台列 `_op`、`_batch`、`_commit_ts`。** 视图从原始层的变更批次（ADR-0006）读出来，带着这三列，映射才能沿用按批次增量合并的语义（#96）。校验用 `DESCRIBE` 拿到视图的列，缺任何一列都拒绝保存。哪张表的平台列代表视图的一行由作者决定，通常是主表。

**保存时校验并预览，敏感列在读之前就换成哈希。** 新建与保存草稿都先在只读湖上执行：先查引用，再在原始层上 `DESCRIBE`（只绑定、不读数据），再取前 20 行样本。不通过不保存，通过后页面展示视图的列与样本。

样本不直接读原始层。会话的本机库 `stage` 里建一个同名 schema，给本数据源的每张原始层表建一个同名视图：采集时像敏感信息的列（`looksSensitive`：列名，或过半取值像邮箱、手机号）和列名命中 `SENSITIVE_NAME` 的列，先换成 `sha256(租户盐 || 取值)`。视图 SQL 在 `USE stage.bronze_<数据源 ID>` 下执行（所以不能带 catalog）。改名、拼接、转成结构体、做类型转换让报错带出取值，见到的都只是哈希（ADR-0005）。

只按输出看不住：`email || ' '`、`name AS _e` 这种改写，单看输出列名和取值格式判断不出来。输出里列名像敏感信息、取值含哈希或含邮箱、手机号的列标为「哈希」，其中还不是哈希的取值再哈希一次，作为最后一道。预览结束删掉这个 schema，不写数据湖、不记审计。

**双人发布，只能由人在页面上发布。** 规则同映射与模板定义（ADR-0015、ADR-0021），共用 `publishBlocker` / `isStale`：
- 每个源视图同时只有一份草稿（`source_view_versions_one_draft_uq`）。
- 发布要有 `publish` 权限，发布者不能是最后保存草稿的人。发布只锁源视图行。
- 起草、保存、丢弃要 `sources:write`，和映射一样。从没发布过的源视图丢弃草稿时整个删除。

发布只有一个入口，就是页面上的 `publish` 表单。它要登录会话（`requirePermission`），没有任务、定时检查或接口会发布源视图，以后也不加。发布不重新执行 SQL：草稿保存时已经校验过，`isStale` 保证发布的就是那份草稿。

## 已接受的取舍

- 源列是否敏感按采集结果和列名猜（宁可误伤），没猜中的源列（如名字叫 `c1`、取值又不像邮箱手机号的姓名列）预览里是明文。原始层本来就存明文（ADR-0005），能看预览的只有能写映射的成员；标准层仍按映射的敏感标记只存哈希。
- 预览里哈希过的源列是文本，对它做数值运算在预览里会报错，真正执行（#96）时不会。列的类型取自原始层上的 `DESCRIBE`，与真正执行一致。
- 预览没有执行时间上限，只受会话的内存与线程限制（同映射空跑）。写得很重的 SQL 会占住一次请求。
- 读本数据源原始层的旧版本（`AT (VERSION => …)`）和读 `_batches` 都放行：它们仍是本数据源原始层的数据。
- 发布时不重新执行：保存后原始层的表若被移出同步范围，要到映射合并时才会报错。
