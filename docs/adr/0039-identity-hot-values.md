# 身份打通统计连了太多记录的匹配值，只告警

占位手机号（`13800000000`）、门店店员代填的号、客服统一留的邮箱，会让一个匹配值连上大量不相干的源记录，传递闭包把这些人合成一个统一消费者。fmcglab 上一个代填号连了 11 条、一个占位号连了 267 条源记录。合并结果本身看不出这类问题，只能在打通时统计（#258，父 issue #254）。

**统计口径。** `resolveIdentities` 建好 `stage.identity_values`（每条源记录在各匹配字段上的取值）之后、求连通分量之前，按 `(rule, value)` 数连上的不同源记录数（`count(DISTINCT node)`），不是统一消费者数：一个值可能只连了一个人的多条记录，也可能连了多个人。值是规范化后的加盐哈希，哈希本身不带字段名（ADR-0005），所以结果里另带 `rule`。达到阈值的值按记录数降序、哈希排序取前 `HOT_VALUE_LIMIT = 20` 个，每项 `{ rule, hash, records, sources }` 写进打通摘要 `IdentitySummary.hot`，随合并任务结果（`tasks.result.identities`）保存；没有时为空数组。`sources` 是数据源 ID，名字在 web 端用平台库换（ADR-0002：工作进程不读平台库）。

**阈值 10。** 真实的人一个号最多是每个 customer 源各一条，租户的 customer 源一般不到 10 个；fmcglab 上代填号连 11 条、占位号连 267 条，阈值 10 两个都能抓到。先用平台常量 `HOT_VALUE_THRESHOLD`，租户还不能改；`IdentityOptions.hotThreshold` 只给测试用。

**只告警，不改合并结果。** 不自动把热值排除出匹配：一个号连 10 条以上也可能是真的（同一个人在多个源、多个账号），自动排除会把真实的人拆开，且拆开与再合上都会在 ID 变更表里留痕（ADR-0029）。是否排除由人看了告警后决定：改映射（清洗规则、去掉匹配字段），或把这个值加进排除列表（见下节）。

**只在质量页和映射页显示。** `/quality`（`sources:read`）列出最近一次成功打通（`latestIdentitySummary`，跳过失败与跳过打通的合并）的 hot：匹配字段、哈希前 16 位（完整哈希放 `title`）、记录数、数据源名；customer 映射的「合并记录」标签页顶部在有 hot 时给一行提示并链到 `/quality`。数据地图任何成员（包括查看者）都能看，不放哈希。页面与结果 JSON 里都只有哈希，没有明文。

**不参与匹配的值。** 合并任务参数 `identityExclude: string[]` 带一份要排除的哈希（#260）：`resolveIdentities` 的 `IdentityOptions.exclude` 在建 `stage.identity_values` 时跳过等于这些哈希的匹配值，效果与映射里写 `nullif` 相同——只靠这个值相连的记录各自成组，其他字段仍能连起来的照样合并；hot 基于同一张表统计，被排除的值不再出现在 hot 里。参数里没有这一项（旧任务）时不排除。
- 按哈希排除，不分字段：哈希不带字段名（ADR-0005），同一个值在手机号与外部 ID 上一起排除。
- 放在任务参数里：工作进程不读平台库（ADR-0002），由入队的一侧汇总进参数（平台表与页面按钮在后续票）。
- 参数里只放哈希，不放明文：工作进程只收 64 位小写十六进制，不合格时任务失败，错误信息不带取值。
- 排除后拆开的大组，旧 ID 的归属照常按「过半继承，否则退役」（ADR-0029）。
- 工作进程不比较排除列表有没有变：数据没变的合并照旧跳过打通，排除列表变了时要由入队的一侧同时带 `identityForce`。

## 已接受的取舍

- 结果里最多 20 项：热值再多时只看得到最热的那些，修好后下次打通再看到其余的。
- 旧任务结果没有 `hot` 时按空数组处理，不提示——要等下一次打通才统计。
- 统计在每次打通都做（一次 `GROUP BY`），跳过打通的合并沿用上次的结果。
