# 指标的字段可写维度路径，基础实体可经一跳引用关联消费者

快消最常用的人群口径都落在商品上，比如近 365 天奶粉消费金额、买过低温鲜奶的人、跨品类数。ADR-0025 的指标写不出这些口径，原因有两个：

- 基础实体必须自己有指向 customer 的 `customer_id`，而 `order_item` 没有；
- filter、measure、window 只能用基础实体自己的字段，而品类在 `product` 上，时间和状态在 `order` 上，`order → order_item` 又是一对多，维度路径走不过去。

结果只能在工作台写 SQL，算出来的数进不了标签和服务库（#255）。这一篇在 ADR-0025 上加两件事，都在计算时关联，标准层不动：

- 字段可以写维度路径（#262）；
- 基础实体可以经一跳引用关联消费者（#263）。

**字段可写维度路径（#262）。** 下面这些位置除了基础实体上的裸字段名，也能写维度路径（如 `order_item.product_id -> product.category`）：

- filter 的 `field`；
- measure 的 `field` 和 `by`；
- ratio 分子、分母的 `field` 和各自的 filter；
- `window.field`。

规则与解析都和维度共用 `resolvePath`：从基础实体出发；相邻两段之间要有关系指向后一段的单列主键（多对一）；最多 3 跳；不成环；终点不能是敏感字段。类型检查按路径的终点字段来做：

- `sum` / `avg` 要求数值字段，window 和 `by` 要求时间字段；
- filter 的取值和 enum 按终点字段的类型来校验。

裸字段名照旧表示基础实体的字段，所以已发布定义编译出的 SQL 逐字节不变。

**编译：**

- 每条路径编译成链式 `LEFT JOIN`。凡是路径前缀相同的，不管来自维度、filter、measure 还是 window，都共用同一组别名，只连一次。走的都是多对一，所以不会多出行。例外是维度之间仍各连一串（别名 `d<维度序号>_<段>`），这样已发布定义编译出的 SQL 逐字节不变；字段路径先复用维度连过的前缀（序号最小的那个维度），其余段新开别名 `p<k>_<段>`，紧跟维度的 JOIN 之后。k 按字段在定义里出现的顺序（filter、measure 的 field、by、分子、分子的 filter、分母、分母的 filter、window）数第几条要新开 JOIN 的路径。只有一段的 `<基础实体>.字段` 等同裸字段，不 JOIN。
- 维度的终点会转成 `VARCHAR`，空值记为「未关联」。filter、measure、window 不这样处理，取的是终点字段的原值：关联不上就是 NULL。所以 `eq` 不命中、`is_null` 命中，`sum` 跳过 NULL，没有时间的行落在窗口之外。
- 和维度一样取当前值（`as_of` 只有 `current`）。
- 依赖（`metricDependencies`）把路径经过的每个实体和各段的字段都计入，定时刷新（ADR-0028）、映射停用影响（ADR-0031）、任务参数里的 `entities` 都会跟着变。

**基础实体经一跳关联消费者（#263）。** 先看基础实体自己能不能关联消费者：它是 customer，或者有一个指向 `customer.customer_id` 的 `customer_id`。能的话，按 ADR-0025 原样处理。这时再写 `consumer_via` 会在发布时报错：「<实体> 自己就能关联消费者」。

自己不能的话，找「一跳」的候选：基础实体上的字段，有关系指向某个实体的单列主键，而且那个实体自己能关联消费者。customer 本身不算候选：指向 customer 的字段如果不叫 `customer_id`（比如推荐人），表示的是另一种归属，不自动认。

- 恰好一条候选：自动走这一跳。
- 多条候选：要求写 `consumer_via: <基础实体字段名>`，写的字段必须是其中一条候选。
- 没有候选：照旧报「基础实体要能关联到消费者」。

只走一跳，多跳等有真实需求时再说。

编译：先 `JOIN` 那一跳的实体（别名 `h`），再 `JOIN silver._identities i ON i._source = h._customer_source AND i.customer_id = h.customer_id`。

- 关联不到那一跳实体的行，或者那一跳实体关联不到消费者的行，都不计入。这和 ADR-0025「关联不到的行不计入」一致：孤儿明细不在指标里处理，由数据质量那边去看。
- filter、window、维度路径里的同一前缀（如 `order_item.order_id -> order.created_at`）共用这个 `h`，不另做 LEFT JOIN。
- `device_attribution` 仍然只有 `base: event` 能写。经一跳关联时只走 `_identities`，不查设备归属。
- `consumer.<字段>` 维度（ADR-0027）对经一跳关联消费者的基础实体也放行：它按 `consumer_id` 连接，和走哪条路关联消费者无关。
- 依赖要计入那一跳到的实体。

模型草稿（ADR-0035）的 `metricContext` 把这类实体也标成可以做基础实体。提示词说明 filter、measure、window 可以写路径，并说明 `count` 数的是基础实体的行数：`base: order_item` 时数的是明细行，要数订单写 `count_distinct order_id`。

`scripts/fmcg-seed/README.md` 的 T5.6 和 T6.3 加上改用指标后的对照：「近 365 天各品类消费金额」按品类分维度，「近 365 天奶粉消费金额」按品类过滤，以及引用后者的「奶粉人群」标签。

## 考虑过的方案

- **合并时把 `customer_id` 冗余进 `order_item`**：不选。这样 `linksToConsumer` 一行都不用改，但标准层要加列、老湖要回填，订单改归属时明细也得跟着重写。这违反 ADR-0019「实体之间在计算时关联、不在标准层冗余」。
- **filter 另起一套路径写法**（如 `{ path: [...], field }`）：不选。和维度两套语法、两套校验，模型草稿也要学两种写法。
- **由编译器自动选候选，不要求写 `consumer_via`**：不选。有多条候选时，自动选一条就是悄悄定了「这一行算谁的」。

## 已接受的取舍

- 路径取当前值：商品改了品类之后，历史订单按新品类算，和维度一样。「按时间点关联」仍然只留了语法位置。
- measure 可以聚合路径终点的字段（如 `sum` `product.price`）。它的含义是「按当前标价，每行算一次」，容易被误用；我们为了规则统一接受这一点，`count_distinct` 写路径（跨品类数）也靠同一条规则。
- 只走一跳：多跳的归属（如 `shipment_item → shipment → order`）现在写不了。
- 带维度的指标仍然不能被标签引用（ADR-0025）。要按品类做标签，就用 filter 把品类定成一个值，做成无维度的指标。
