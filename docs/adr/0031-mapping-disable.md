# 映射停用：记在映射上、双人确认，停用后不再算作已发布

已发布的映射以前只能改、不能撤下（ADR-0015；ADR-0030「没有撤下映射的路径」）。源表废弃、映射写错了实体、两份映射重复写同一批数据时，只能发一版空转的映射凑合（#156）。

**记在映射上，不加版本状态。** 停用是映射本身的状态，记在 `platform.mappings` 的 `disabled_at` / `disabled_by_email` 上，不往 `VERSION_STATUSES` 里加值：那个枚举还被模板、源视图、自定义实体共用，而且停用针对的是整个映射，不是某一版。代码里叫 disable，中文叫「停用映射」，与租户的「停用（Suspension）」不是一回事。

**双人确认。** 与发布一样要两个人（ADR-0015）：一位有 `publish` 权限的成员提议（`requestDisable`，记 `disable_requested_by_email` / `disable_requested_at`，已有提议时覆盖原提议人），另一位有 `publish` 权限的成员确认（`confirmDisable`，确认人不能是提议人）。确认后写 `disabled_at`，停用人记为提议人，清掉提议列；确认人记在审计 `mapping.disabled` 的 detail 里（提议记 `mapping.disable_requested`）。两步都先锁租户行再锁映射行，与发布、入队合并互斥。没有已发布版本的映射不用停用，丢弃草稿即可。

**停用后不再算作已发布。** 「已发布映射」的读取方都跳过停用的映射：`publishedPlans`（由此带到入队合并、身份打通规则、键空间与主键独占检查、数据地图与血缘、主键体检、敏感字段判断、关系建议）、同步后的合并 `mergeAfterSync`、定时检查 `dueMappings`，以及自定义实体的引用方 `publishedReferrers`、草稿检查里跨源引用的目标源要有已发布的 `customer` 映射（`customerSources`，目标源的都停用了就写不进新的引用）。只是提议时照常算。停用的映射因此也让出了主键独占与键空间的位置。

**被跨源引用的 customer 映射不能停用。** 别的数据源的映射用 `customer_source` 指向这个数据源时（ADR-0030，`crossSourceReferrers`），停用它的 `customer` 映射会让这些引用找不到消费者。提议和确认两步都检查（提议之后才发布的引用也拦），报错列出引用方（数据源 + 映射名与字段），先改掉或停用引用方。

**停用后合并撤下它的行（#194）。** 确认停用的同一事务里入队一次合并：参数 `drop: { mapping, entity }[]` 与 `mappings` 并列，`mappings` 带同实体其余已发布的映射。合并在各实体并行合并之前逐个撤下 drop 里的映射：一个事务里删掉它在 `silver.<entity>` 的行（表还不在时跳过）、`silver_records` 里它的当前记录与 `silver._merges` 里它的水位（之后再合并它就走重建），结果里记在 `dropped`。撤下的是 `customer`、`event` 或 `consent` 的映射时强制重算身份打通。同实体其余映射一起合并，是因为失败的合并不自动重试（ADR-0015）：原先因为和它冲突而失败的映射要在这次补上。已有合并在排队时并进去：从它的 `mappings` 里剔除停用的映射、`drop` 并在一起；已有合并在运行时确认停用报错、不停用，等它结束再确认（运行中的合并参数改不了，撤下的行会没人删）。

**恢复（#195）。** `restoreMapping` 只要一位有 `publish` 权限的成员，不用双人确认：恢复的是两个人发布过的版本，不引入新内容。停用期间别的映射可能占了它让出的位置，所以恢复前先锁数据源的源表行（与修改同步范围同序）、租户行和映射行，再拿最新已发布版本重跑发布时的检查：对照数据源当前的字段、已发布登记与跨源目标重新校验文档（`checkMappingDraft`；登记已删的实体在这里拦下），然后跑 `assertPublishable`（扩展字段类型、身份规则、键空间、跨源引用的 customer 键空间、指标引用的字段，与 `publishMappingDraft` 共用）。主键独占和发布时一样，不在恢复时检查，而是由随后的合并检查（ADR-0024）：别的映射占了它的主键时，恢复会成功，但那次合并失败，报「主键 … 跨映射重复」，标准层不变。源表（输入是源视图时，视图引用的表）不在同步范围时拒绝恢复，要先选回，否则重建读不到批次。通过后清掉 `disabled_at` / `disabled_by_email`，记审计 `mapping.restored`，并在同一事务里入队带 `rebuild` 的合并（撤下时已删掉它的水位）。已有合并在运行时报错，不恢复；确认停用后撤下它的合并还在排队时恢复，那次合并同时带着它的 `drop` 和重建，先撤下再重建，结果一样。

**停用期间不再拦源表。** 停用的映射不算「已被已发布映射引用」，源表因此可以移出同步范围（`setSyncScope`）；源表列差异检查（`mappingDrift`）也跳过它。

## 已接受的取舍

- 本期不做撤回提议：提议放着不确认不影响任何读取方，需要时由别人再提议覆盖。
- 合并在运行时不能确认停用，要等它结束再确认；不另做排队等它结束再停用的机制。
- 跨源引用只看「这个数据源有别的数据源引用」，不看同源是否还有别的已发布 `customer` 映射：一个数据源通常只有一个 `customer` 映射，而且键空间由各 `customer` 映射汇总，停掉其中一个也可能让引用失效。
- 停用的映射不算自定义实体的引用方，实体因此可以删掉，留下目标实体已不存在的停用映射；恢复时重跑发布校验会拦下它（#195）。
- 恢复时重新对照数据源当前的字段校验文档：停用期间源端删掉了它引用的列，恢复就被拒，要先改一版草稿发布（发布不拒绝停用的映射）再恢复。
- 恢复时不查主键独占：在请求里检查就要只读挂载数据湖，并对源表做一遍完整转换，大表太慢。所以和发布一样，冲突在合并时报出，映射算已恢复，由成员停用占位的一方或声明键空间后再合并。
