# 映射停用：记在映射上、双人确认，停用后不再算作已发布

已发布的映射以前只能改、不能撤下（ADR-0015；ADR-0030「没有撤下映射的路径」）。源表废弃、映射写错了实体、两份映射重复写同一批数据时，只能发一版空转的映射凑合（#156）。

**记在映射上，不加版本状态。** 停用是映射本身的状态，记在 `platform.mappings` 的 `disabled_at` / `disabled_by_email` 上，不往 `VERSION_STATUSES` 里加值：那个枚举还被模板、源视图、自定义实体共用，而且停用针对的是整个映射，不是某一版。代码里叫 disable，中文叫「停用映射」，与租户的「停用（Suspension）」不是一回事。

**双人确认。** 与发布一样要两个人（ADR-0015）：一位有 `publish` 权限的成员提议（`requestDisable`，记 `disable_requested_by_email` / `disable_requested_at`，已有提议时覆盖原提议人），另一位有 `publish` 权限的成员确认（`confirmDisable`，确认人不能是提议人）。确认后写 `disabled_at`，停用人记为提议人，清掉提议列；确认人记在审计 `mapping.disabled` 的 detail 里（提议记 `mapping.disable_requested`）。两步都先锁租户行再锁映射行，与发布、入队合并互斥。没有已发布版本的映射不用停用，丢弃草稿即可。

**停用后不再算作已发布。** 「已发布映射」的读取方都跳过停用的映射：`publishedPlans`（由此带到入队合并、身份打通规则、键空间与主键独占检查、数据地图与血缘、主键体检、敏感字段判断、关系建议）、同步后的合并 `mergeAfterSync`、定时检查 `dueMappings`，以及自定义实体的引用方 `publishedReferrers`、草稿检查里跨源引用的目标源要有已发布的 `customer` 映射（`customerSources`，目标源的都停用了就写不进新的引用）。只是提议时照常算。停用的映射因此也让出了主键独占与键空间的位置。

**被跨源引用的 customer 映射不能停用。** 别的数据源的映射用 `customer_source` 指向这个数据源时（ADR-0030，`crossSourceReferrers`），停用它的 `customer` 映射会让这些引用找不到消费者。提议和确认两步都检查（提议之后才发布的引用也拦），报错列出引用方（数据源 + 映射名与字段），先改掉或停用引用方。

**之后的票。** 停用的映射以前写进标准层的行由停用后的合并去掉（#194）；恢复（#195）时重新跑发布时的校验（主键独占、键空间、跨源引用、扩展字段类型等），因为停用期间别的映射可能已经占了它让出的位置；页面上的按钮由 #196 做。

## 已接受的取舍

- 本期不做撤回提议：提议放着不确认不影响任何读取方，需要时由别人再提议覆盖。
- 确认停用时不从已在排队的合并里拿掉这个映射，也不入队合并（#194 处理）。
- 跨源引用只看「这个数据源有别的数据源引用」，不看同源是否还有别的已发布 `customer` 映射：一个数据源通常只有一个 `customer` 映射，而且键空间由各 `customer` 映射汇总，停掉其中一个也可能让引用失效。
- 停用的映射不算自定义实体的引用方，实体因此可以删掉，留下目标实体已不存在的停用映射；恢复时重跑发布校验会拦下它（#195）。
- `sources.ts` 判断表是否被已发布映射引用、`source-drift.ts` 的列差异仍按「有已发布版本」判断，停用的映射照样算，留给 #195 一起处理。
