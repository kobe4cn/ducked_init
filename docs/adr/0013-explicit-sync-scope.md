# 成员逐张选定同步范围，只采集与同步范围内的表

原先的做法是：最近一次采集到的表全部同步，只跳过有水位线候选、但还没确认水位线的表。一个数据源动辄几百张表（字典表、日志表、临时表、与 CRM 无关的人事和财务表），这样做有三个问题：
- 没有水位线候选的表一律全量比对（ADR-0010），无关的表也要每天甚至每小时整表读一遍，占用租户的配额。
- 原始层保留每一批次（ADR-0006），敏感信息明文加密存在原始层（ADR-0005），删除请求也要清到原始层。无关的表进湖，等于主动扩大要保护、要清除的范围。
- 想不同步某张表，只能故意不确认水位线，把水位线确认当开关用；没有水位线候选的表则根本无法排除。

现在改为**同步范围**：成员为每个数据源逐张选定要同步的表，记在 `source_tables` 上（是否选中、选中人、选中时间），与水位线、业务主键的确认方式一致。

**采集分两步。**
1. 列出表：沿用测试连接的做法，只取表名、schema、读权限，以及源端能廉价给出的估算行数（PostgreSQL 的 `pg_class.reltuples`、MySQL 的 `information_schema.TABLES.TABLE_ROWS`；其他数据源不给）。不读任何行。
2. 采集列统计：只对同步范围内的表抽样，得到列统计、水位线候选与业务主键候选。表被选入范围时，为它入队一次采集。

这样成员选表时只看得到表名和估算行数，看不到列统计。列统计里有样本的最小值、最大值（可能就是手机号、姓名），不在范围内的表不应该把它们写进任务结果。

**规则。**
- 新登记的数据源，以及重新列出表时新出现的表，默认不在范围内。
- 只保存显式的表清单，不保存通配或按 schema 的规则。界面可以按 schema 全选、按名称过滤后批量选，但保存下来的仍是逐张的表；否则新出现的表是否会自动进湖就不透明了。
- 范围内、有水位线候选、还没确认水位线的表，不同步，并在数据源页标为“待确认水位线”，不再静默跳过。没有候选的表直接全量比对。
- 移出范围：停止采集与同步，原始层、当前主键状态与镜像都保留。要清除数据另做显式操作，不和移出范围绑在一起。
- 重新选回：水位线表从 `_batches` 记录的位置继续（ADR-0012），回看窗口补不上的间隔由下一次比对补齐；全量比对的表下一次比对时自然补齐。
- 已被映射引用的表不能移出范围（映射上线后生效）。
- 源端删掉了范围内的表：列出表时标为“源端已不存在”，同步跳过，不自动移出范围。

**迁移。** 已有的数据源：原始层里已经有的表回填为在范围内，同步行为不变；其余表不在范围内。

## 已接受的取舍

- 新登记的数据源多了一步选表，接入向导要把它放在登记之后、生成映射草稿之前。
- 选表时只有表名和估算行数可参考，看不到列的情况；选入后要等采集完成才能确认水位线、声明业务主键。
- 源端新增的表不会自动进湖，成员要回来选。数据源页提示“有 N 张新表未选”。

## Considered Options

- 默认全选、成员排除：现有数据源不用迁移，但无关的表在成员发现之前已经进湖，敏感信息也已落进原始层，事后排除不能撤回。否决。
- 按 schema 或名称通配保存范围：表多时配置省事，但新表会在成员不知情时进湖。暂不采用。
- 先对全部表采集列统计、再选：选表时信息最全，但表多时采集很重，且无关表的样本统计会写进任务结果。否决。
