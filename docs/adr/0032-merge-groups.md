# 合并组：同一批对象的多路接入按存活规则在标准层只留一行

ADR-0024 把跨映射的主键默认定为独占，并留了一个方向：同一批对象从几个数据源接入（第 2 种，两套系统都存了同一批订单）或由几个数据源各自维护一部分字段（第 3 种）时，由成员显式声明「这几个映射描述的是同一批对象」与存活规则。现在落实这个方向，叫合并组（merge group）。

**存放。** 平台库新表 `merge_groups(id, tenant_id, entity, created_at)`，`(tenant_id, entity)` 唯一，即每个实体最多一个合并组；`merge_group_versions(id, group_id, version, status, members, rule, authors, last_editor, published_by_email, published_at, updated_at)`，每组同时只有一份草稿（与 `custom_entity_versions` 一样的两个唯一索引）。`members` 是映射 ID 的有序数组，顺序即优先级；`rule` 是 `{ kind: 'priority' } | { kind: 'latest', field } | { kind: 'coalesce' }`。第一次保存草稿时建组，从没发布过的组丢弃草稿时删除。代码在 `app/.server/merge-groups.ts`，规则类型与名称在 `app/lib/merge-groups.ts`。

**存活规则。**

- `priority`（按优先级）：整行取优先级最高、有这个键的映射。
- `latest`（取最新）：整行取 `field` 最新的一边，一样新时按优先级。
- `coalesce`（逐字段补齐）：逐个字段按优先级取第一个非空值。

`_mapping` / `_source` 记整行胜出的映射（`coalesce` 下是有这个键的最高优先级映射）；customer 引用列旁的 `_customer_source`（ADR-0030）跟随该列取值来自的映射，不跟整行。

**起草与发布。** 按映射的规则双人发布（ADR-0015，`publishBlocker`）：起草与丢弃要 `sources:write`，发布要 `publish`，发布者不能是最后保存草稿的人；发布后版本锁定，再改是新的一版草稿，丢弃回到已发布版本。审计 `merge_group.saved` / `merge_group.published` / `merge_group.draft_discarded`。保存与发布都校验（`checkMergeGroup`，纯函数），不通过时什么也不存：

- 组员至少 2 个，每个映射在组里只出现一次；
- 组员都是这个实体已发布、未停用（ADR-0031）的映射；
- 组员的 `key_space` 相同（或都不写）：键空间不同说明编号各自独立（ADR-0024 第 1 种），不是同一批对象；
- 实体不是 `customer`（ADR-0027 已有属性取舍），也不是主键只在同一数据源内唯一的实体（`uniqueBySource`，如 `consent`）：这类实体的人层面取舍在统一消费者上做；
- `latest` 的字段是这个实体的字段（标准实体或已发布登记的字段，加上组员写的扩展字段）。

保存与发布都先锁租户行（`lockTenant`，与停用、发布映射互斥）再锁组行；保存之后组员可能被停用或改了键空间，所以发布时再校验一次。页面上组员显示为 `「数据源」源表 → 实体`，优先级要填各不相同的正整数，留空即不在组里。

**合并（#198、#199）。** 组员照旧各写 `silver_records` 与 `_merges` 水位；写标准层时删掉组内全部组员在受影响主键上的行，再按规则从全部组员的当前记录重算写入。独占检查跳过同组映射，组外照旧失败。发布组时在同一事务里给组员入队带 `rebuild` 的合并。`publishedMergeGroups(db, tenantId)` 给出每个实体最新的已发布组，供合并使用。

#198 的做法：`publishedPlans` 给组员的合并参数带上 `group = { id, rule, key, members }`，`key` 是实体主键（不是各映射的去重键），`members` 只列可用的组员（已发布、未停用、仍写入该实体，按优先级），每个带上数据源、版本、去重键、取最新字段、键空间与 customer 引用列的数据源，工作进程不读平台库；可用组员不到 2 个时不带。组员合并时先照常写自己的当前记录，再在同一事务里删掉全部组员在标准层的行，从各组员的当前记录（每个去重键取最新的一行，与单独合并时一样）按规则重算写回：每次整组重算，只算受影响的键留给 #199。主键有空值的行不并，各自一行；还没有当前记录的组员视为空。发布组时入队的映射还包括上一版里被移出组的映射（它们要写回自己的行，与组撞键时按独占失败）；合并在运行时拒绝发布。标准层写法（合并日志的 `scheme`）改为 3，各映射下次合并时重建一次。

**合并记录（#200）。** `MergeRecord.group = { overlap, conflicts: [{ field, count, samples }] }`，只统计本次重算的键；样本只带主键，敏感列只计数。

**停用与恢复（#199）。** 组员被停用或恢复时，组内其余映射带 `rebuild` 入队；可用组员不到 2 个时组失效，组员之间恢复独占检查。

**冲突体检（#200）。** 同一已发布组内的映射对不报冲突；判为重复接入的建议改为「可以建合并组」。

## 已接受的取舍

- 每个实体最多一个合并组。一个实体下有两批互不相干的多路接入时，用键空间把它们分开；真遇到了再放开。
- customer 不建合并组：同一个人在多个数据源里由身份打通归并，属性按 ADR-0027 取舍，再叠一层组会有两套存活规则。
- 校验只在保存与发布时做。发布之后组员被停用、改了键空间，由合并（#199）判断组是否还有效，不回头改已发布的组。
- 第一期（#197）只做设置的存放、编辑与发布，发布组不入队合并：引擎还不认组，入队会因独占检查失败。#198 接上合并。
- 合并组页只列能建组、且有至少 2 个已发布未停用映射的实体（以及已有组的实体），不提供 customer 与 `uniqueBySource` 的实体；接口仍按上面的规则拒绝。
