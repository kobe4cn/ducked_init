# 水位线增量同步：数据源与数据湖挂在同一个 DuckDB 里，批次日志随变更批次写进数据湖

对已确认水位线字段的表，平台每小时同步一次，把变化作为变更批次（ADR-0006）追加到原始层。工作进程在同一个 DuckDB 里先挂载本租户的数据湖，再以 `src` 只读挂载数据源（ADR-0009），然后锁住配置（ADR-0008）。这样数据可以直接从源端写进湖里，不经过本机文件。两边都在对象存储上时，两把 S3 凭据用 `SCOPE` 各自限定在自己的前缀上。

原始层按数据源分 schema：`bronze_<数据源 ID>`。每张源表对应一张原始层表，包含源表的全部列，再加四列：
- `_op`：新增、更新或删除。
- `_commit_ts`：源端提交时间。
- `_batch`：批次号，每张表从 1 起递增。
- `_synced_at`：同步时间。

同一 schema 里还有一张 `_batches` 批次日志，记录每张表每个批次的方式、水位线起止、实际读取的起点和各操作的行数。它与变更批次在同一个 DuckLake 事务里写入，是下一次同步起点的唯一依据。这样即便调度器没来得及记下任务结果，下一次同步也会从湖里实际写入的位置继续，不会重复或跳过批次。成员在数据源页看到的同步历史来自 `source.sync` 任务的结果。

有主键的表另在 `bronze_<数据源 ID>_keys` 里保存**当前主键状态**：每个仍存在的主键一行，带最新一版的整行哈希，随变更批次在同一个事务里更新。主键是源端主键（MongoDB 为 `_id`）；源表没有主键时，成员可以从平台给出的候选（样本中非空、取值唯一的整数、文本或 UUID 列）里确认一个**业务主键**。当前主键状态不存在或主键变了时，由原始层重建（每个主键取最新一版，去掉最新一版是删除的）。

一次同步：
1. 读取这张表最近一个批次。如果它用的不是当前的水位线字段（首次同步，或成员换了字段），这次就全量读取。否则从水位线往回退一个**回看窗口**读起：更新时间与 ObjectId 往前 `SOURCE_SYNC_LOOKBACK_MINUTES`（默认 15 分钟），整数自增主键往前 `SOURCE_SYNC_LOOKBACK_IDS`（默认 1000 个）。PostgreSQL 与 MySQL 的条件写进经 `postgres_query` / `mysql_query` 发往源端的查询，在源端执行，不依赖扩展的条件下推。MySQL 带时区的时间换成 `FROM_UNIXTIME(…)`，由 MySQL 按会话时区换算，各版本都支持。其他数据源在 DuckDB 里过滤：Parquet 可以按行组统计跳过数据；MongoDB 与 CSV、JSON 文件做不到，要整表读过一遍。
2. 回看窗口补的是水位线天然会漏的行：长事务在上次同步之后才提交、但更新时间早于水位线（PostgreSQL 的 `now()` 取事务开始时间），或自增主键分配在前、提交在后。回看重读到的行，没变的不再写入：有主键时，与当前主键状态里的整行哈希比对；没有主键时，与原始层里同一范围的行比对。整行哈希对“列名=取值”的文本按列名排序后计算，空值不参与。所以源表新增字段、列顺序或类型变化，都不会让没变的行被当成更新。
3. 有主键时，读取的行先校验主键非空且唯一（业务主键只基于样本确认，不满足时这张表同步失败并说明原因）。当前主键状态里有的记为更新，否则记为新增。没有主键的表一律记为新增。
4. 同步后的水位线取原水位线与本次读到的最大值中较大的一个，回看不会让它后退。
5. 更新时间水位线的提交时间取该字段（不带时区的时间一律按 UTC 解读：工作进程的 DuckDB 会话固定用 UTC，结果不随所在机器的时区变化）。自增主键拿不到提交时间，用同步时间代替。
6. 源表新增的字段，在原始层随之加列。
7. 有主键的表，距上次读全集（全表读取或主键比对）满 `SOURCE_RECONCILE_HOURS`（默认 24 小时）时，紧接着再比对一次**主键全集**，单独产出一个批次，水位线不变。只从源端读取主键列（PostgreSQL 与 MySQL 在源端执行）：
   - 当前主键状态里有、源端已没有的主键，追加一条只带主键列的**删除**记录；
   - 源端有、当前主键状态里没有的主键（回看窗口也没补上的行），读取整行后记为新增。漏掉的主键不多时，按主键分批发往源端查询；否则整表读取后筛选。

这样 ADR-0006 要求的删除记录也由水位线同步产出，标准层仍然只消费变更批次。映射里声明的软删除字段照样可用，它在标准层解释，与这里的删除记录不冲突。

大批次、比对超出内存上限时，工作进程溢写到每个任务专用的本机临时目录（上限为内存配额的 10 倍），任务结束即删除（与 ADR-0010 相同）。

同一数据源同时只有一个同步在排队或运行：入队前锁住数据源行，再检查已有的任务。常驻调度器每分钟检查一次到期的数据源，同步周期由 `SOURCE_SYNC_INTERVAL_MINUTES` 设定，默认 60 分钟。成员可以随时手动触发一次。每张表各用一个事务，一张表失败不影响其他表。有表失败时，任务记为失败，结果里保留各表的批次与错误。

## 已接受的取舍

- 删除最迟要等一个比对周期（默认一天）才进原始层，删除记录的提交时间是比对时的同步时间。需要更及时时，在映射里声明软删除字段，或缩短 `SOURCE_RECONCILE_HOURS`。
- 比对主键全集要在源端扫一遍主键（通常只走主键索引），并把主键全集传到平台。
- 没有主键、也没确认业务主键的表，看不到删除，增量行一律记为新增。回看窗口里内容完全相同的两行，也只会写入一行。
- 超出回看窗口才提交的修改（主键已经存在）不会被发现，主键全集比对只补缺失的主键。遇到比窗口更长的事务，调大 `SOURCE_SYNC_LOOKBACK_MINUTES`。自增主键水位线只能发现新增，发现不了修改（ADR-0011 对 ObjectId 也有同样的说明）。
- 整行哈希是 64 位。两个不同版本哈希碰撞的概率可以忽略；一旦碰撞，这次修改会被当成没变。
- 当前主键状态每批次都会删改，DuckLake 里会积累小文件和删除文件，需要定期合并（与其他表的维护一起做）。
- 同一数据源的互斥只在入队时检查。任务被判为失联后，调度器会终止对应的工作进程；调度器与平台 PG 失联过久时，会终止全部工作进程。因此不会有两个同步同时写同一批原始层表。
- 同步历史存在任务结果里，只列出最近 50 次同步。完整记录在数据湖的 `_batches` 里。

## Considered Options

- 数据源与数据湖各开一个 DuckDB，在进程内用 Arrow 搬数据：隔离更直观，但要自己分批搬运，大表时更复杂。不采用。
- 水位线存进平台 PG：页面读起来方便，但与湖里的数据不在同一个事务里。任务写完湖、没来得及记下结果时，会重复或漏掉一个批次。不采用。
- 判断新增还是更新时直接扫原始层的全部历史：不用多存一份状态，但开销随历史增长，回看去重和主键比对也要先求出每个主键的最新一版。不采用。
- 没有主键的表按整行哈希的多重集比对（ADR-0010 的无键做法）：能发现删除，但每次都要整表读取，等于全量比对。这类表建议确认业务主键；实在没有，就改用全量比对。
