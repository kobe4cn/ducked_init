# 结果层定时刷新：依赖的实体有新合并后，每天按生效版本重算指标与下游标签（以及分析模板），快照记来源

ADR-0025 定下「发布只算最新快照，回刷手动」：指标与标签只在发布那天算一次，之后标准层合并了新订单，结果层不会跟上。#143 要让已发布的指标与标签随标准层的变化每天刷新，并让人看得出一张快照是怎么来的。

**什么时候算。** 调度器每次检查（`scheduleSyncs`，排在快照过期之后）调用 `enqueueDueRefreshes()`（`app/.server/refresh.ts`）。对每个已发布的定义（各自最新的已发布版本）：它依赖的实体在它最近一次 `gold.dsl` 任务（任何状态）提交之后，有结束了的 `silver.merge` 改到了数据，就以当天（UTC）为 `asOf` 按生效版本入队一次 `gold.dsl`。

- 依赖的实体是任务参数里的 `entities` 再加上 `customer`：所有指标都要关联 `_identities`，而身份打通只随 customer 或 event 的合并重算（#167）；event 指标已经把 event 算在 `entities` 里。
- 「改到了数据」看合并任务的 `result.mappings`：有一条记录的 `entity` 属于依赖的实体，且 `inserted + updated + deleted > 0` 或 `mode = 'rebuild'`。合并任务成功或失败都看（每个映射单独提交，失败的任务里也可能有映射已经改了数据）。只读平台库，不开 DuckDB。

**入队规则。**
- 每个租户一个事务，先锁住租户行（与发布、回刷、另一个调度器互斥）；租户已停用时跳过。
- 租户有合并在排队或运行时，这次整个租户都跳过，保证同一 `asOf` 的指标与标签读到同一份标准层。
- 指标与引用它的已发布标签（按生效版本的指标内联，不再通过校验的跳过并记进审计）在同一个事务里入队；某个下游标签已有任务在排队或运行，就只跳过这个标签（当天已有快照的下游标签照样随指标重算，与指标读同一份标准层）。
- 定义已有任务在排队或运行，或当天已有当前版本的未过期快照时，不再入队。
- 标签自己依赖的实体有变化、而它引用的指标已经按新合并算过（如合并之后发布了指标新版本）时，单独入队这个标签。
- 每个入队的定义记一条审计 `definition.refreshed`，操作者是平台（`{ tenantId, system: true }`）。

**模板也适用（#179）。** 已发布的模板（如 RFM，各自最新的已发布版本）在同一个租户事务里、指标与标签之后检查，规则相同：依赖的实体取 `TEMPLATES[模板].entities`（RFM 是 `order`、`customer`），「最近一次计算」是本租户这个模板的最近一次模板任务（如 `gold.rfm`，任何状态）；模板按模板去重（每个租户一个定义），已有任务在排队或运行、或当天已有当前版本的未过期快照时跳过；以生效版本的参数加上当天的 `asOf` 入队，来源 `scheduled`，审计 `template.refreshed`。模板发布入队的任务来源记 `publish`，「重新计算」记 `manual`（ADR-0021）。有已发布模板而没有已发布指标或标签的租户同样检查。映射首次合并后平台按默认参数自动启用的模板（ADR-0021，#230）也是已发布的模板，之后由这里接管定时刷新。刷新同样经 `enqueueTemplate` 入队，任务按生效版本锁定的模板版本编译（`templateVersion`，ADR-0021），不随注册表升级。

**快照记来源。** `platform.snapshots` 新加 `trigger text`：`publish`（发布）、`backfill`（回刷）、`scheduled`（定时刷新）、`manual`（手动）；这一列之前的老快照为空。`gold.dsl` 与模板任务（如 `gold.rfm`）的任务参数带上 `trigger`，登记快照时从任务参数里读（快照的 `params` 来自任务结果，里面没有它）；不在取值范围里或没写时为空。指标与标签的定义页另有「重新计算」（#180）：有发布权限的成员按当天以生效版本入队（指标连同下游标签，去重同回刷），来源 `manual`，审计 `definition.recomputed`；定义页显示最近一张未过期快照的时间与来源，分析页快照列表显示来源。

## 已接受的取舍

- 只要依赖的实体有改动就整份重算，不判断改动是否落在指标的过滤条件或时间窗口里。
- 每个定义每天最多一张定时刷新的快照：当天已有当前版本的快照后，同一天再有新合并也不再算，第二天才跟上。
- 依赖只按实体判断，不看改到了哪些字段；customer 的任何改动都会让全部指标重算。
- 「每天固定时刻」「仅手动」等刷新策略不在这里，见 #143。
- 没写结果就结束的合并（崩溃、超时）没有 `result.mappings`，不算「有新合并」；它之前提交的映射改到的数据要等下一次合并才带上刷新。
- 判断看的是定义最近一次 `gold.dsl` 的提交时间，不管它成没成功：定时刷新的任务失败后，要等下一次改到数据的合并才再算。
