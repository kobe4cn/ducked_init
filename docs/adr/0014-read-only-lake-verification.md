# 湖中数据核对只读挂载数据湖、只出报告，修复只走同步

成员需要知道每张源表的数据进了湖里的什么位置、文件是否真实存在、结构与数据量是否与源端一致。只看同步历史回答不了：同步记下的是写入了什么，看不出文件后来丢了、源端删了行而湖里还在，也看不出从未同步过的表。因此新增核对任务 `source.verify`，从**源端的全部表**出发（只从湖这一侧往回查，会漏掉从未进湖的表），每张表标出覆盖情况与源端行数；已进湖的表再核对位置、文件、结构与数据量四项。

**只读。** 核对与同步一样在工作进程里运行，只用租户自己的凭据（ADR-0001、0008、0009），但数据湖以 `READ_ONLY` 挂载：任何写入都会被 DuckDB 拒绝，而不是靠代码自觉。比对的中间结果只放在任务临时目录里的本机库 `stage`（ADR-0010），任务结束即删除。发现差异时，成员在页面上触发一次带主键比对的同步（`source.sync` 加 `reconcile`，不等比对周期），修复只走同步这一条写入路径，核对本身从不改写原始层、主键状态、镜像或目录。

**四项怎么核对。**
- 位置：原始层 schema 与表名、数据文件所在的存储前缀（取自 DuckLake 目录）、当前主键状态或镜像的位置。
- 文件：直接读 DuckLake 目录库里的 `ducklake_data_file`、`ducklake_delete_file`、`ducklake_files_scheduled_for_deletion`、`ducklake_column` 与内联数据表，与存储上实际的文件对照：登记的文件（含历史快照仍引用的）都要存在且大小一致；当前数据文件读 Parquet 尾部元数据，行数与目录一致、字段都是目录里有的列；表前缀下存在、目录未登记、也不在待删除清单里的文件报告为孤儿文件，不删除；内联在目录库里的小批次单独列出行数。
- 结构：以核对时实时读取的源表结构为基准与原始层对照。湖中缺列（源端新增字段）与类型不同（区分源端放宽与不兼容）算差异；湖中多出的列（源端删除字段）是保留旧列的预期结果，只列出、不算差异。处理规则另定（#22）。
- 数据量：有主键（源端主键或业务主键）的表比对源端主键全集（软删除字段标记为删除的不算）与原始层回放后的当前主键，与每日主键比对同一机制，同样按主键的哈希分桶；湖中缺失的主键里，水位线晚于最近一次同步上界的是同步后新增的，标为待下次同步、不算差异。缺失与多出各给出前 20 个主键。没有主键的表比较源表行数与原始层回放后的行数。

**覆盖。** 源端每张表标为已进湖、不在同步范围、等待采集、待确认水位线、等待首次同步、同步失败或账号没有读权限之一（原先设想的“同步方式尚未支持”在全量比对上线后已不存在，ADR-0010）。源端已没有、湖中仍有的表（或同步范围内的表）标为源端已删除，只报告，不算差异：主键比对修不了它。已移出同步范围的表只核对位置与文件，湖中数据不再更新不算差异（ADR-0013）。

**触发与互斥。** 成员手动触发，调度器每天（`SOURCE_VERIFY_INTERVAL_HOURS`，默认 24 小时）为每个有要同步的表、租户未停用的数据源入队一次。同一数据源的同步与核对互斥：入队前锁住数据源行，有任何一个在排队或运行时拒绝（调度器等下一次检查），核对不会读到写了一半的批次。结果存在任务结果里，数据源页展示最近一次成功的核对，数据源列表标出有差异的数据源；不做通知或告警。查看需要 `sources:read`，触发核对与主键比对需要 `sources:write`。

## 已接受的取舍

- 每次核对都要在源端统计每张可读表的行数（含不在同步范围内的表），并读一遍已进湖表的主键全集，开销与每日主键比对相当。PostgreSQL 与 MySQL 在源端执行，只传回结果。
- 读不了的表只能给出源端的估算行数（PostgreSQL、MySQL），其他数据源没有。
- 直接读 DuckLake 目录库的内部表，与 DuckLake 的元数据格式绑在一起；升级 DuckLake 时要回归核对的测试。待删除清单不带表 ID，按完整路径对照（相对路径相对于数据湖的存储前缀）。
- 主键样例写进任务结果（平台 PG），业务主键可能是邮箱等敏感信息。只给前 20 个，且只针对已进湖的表。
- 有水位线、没有主键的表在两次整行比对之间，修改以新增记入原始层，核对会看到湖中行数多于源端；触发主键比对（整行比对）即可纠正。没有水位线的全量比对表，上次同步之后源端新增的行同样报告为湖中缺失，没有水位线可以判断是否“同步后新增”。

## Considered Options

- 核对时顺手修复（直接补写缺失的行、删掉孤儿文件）：省一步，但会多出一条绕开批次日志与主键状态的写入路径，原始层不再只由同步产出（ADR-0006、0012）。否决，修复只走同步。
- 只核对已进湖的表：实现简单，但从未同步过的表（待确认水位线、账号读不了、不在范围内）不会出现在报告里，正是成员最容易漏看的。否决。
- 用 `ducklake_list_files` 代替读目录内部表：只覆盖当前快照的文件，找不出孤儿文件与历史快照丢失的文件。不采用。

## 补充：标准层的漂移检查（lake.inspect）

漂移检查沿用同样的做法：工作进程只读挂载数据湖（与合并共用锁定引擎与配额，ADR-0008），对比 `silver` 下标准层表的实际结构与「标准模型 + 已发布映射」推出的应有结构（ADR-0015），报告缺列、多列、类型不一致与没有映射写入的孤表，结果只写进任务结果，不改湖。修复走合并，不另开写入路径。应有结构在入队时由平台算好放进任务参数（工作进程不连平台库）；成员在数据地图上手动触发（需 `sources:write`），同一租户同时只有一次在排队或运行。报告里只有标准层的表名、列名与类型，不含源表名，任何角色都能看最近一次结果。合并只给标准层表加列、不删列，映射新版本去掉的扩展字段会一直报「多列」，这是预期的。
