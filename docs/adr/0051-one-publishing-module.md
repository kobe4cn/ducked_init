# 可发布项的保存、发布、丢弃由一个模块负责，审计永远是事务里最后一步

可发布项（CONTEXT.md）有七种：映射、源视图、指标定义、标签定义、模板定义、自定义实体、合并组。它们的版本表形状相同，规则也相同：同一时刻最多一份草稿，双人发布，加锁后比对 `updatedAt` 做过期检查，丢弃从没发布过的项时连父行一起删。但这套流程在 `mappings.ts`、`dsl-definitions.ts`、`templates.ts`、`custom-entities.ts`、`merge-groups.ts`、`source-views.ts` 里各写了一遍，`publish-rules.ts` 只提供谓词。加锁顺序、审计放在哪里这些约束只靠调用方自觉：模板和源视图把审计放在入队之后，因为记目录版本拿的锁要是事务里最后一个锁（ADR-0047），其余四处却放在入队之前。

决定：**保存草稿、发布、丢弃由 `app/.server/publishing.ts` 一个模块负责，每种可发布项通过适配器接入。适配器提供表、要不要先拿租户锁、事务外检查（可访问 DuckDB 或数据湖）、事务内检查（只查 PG）、发布后动作和丢弃后动作。发布的顺序固定为：读草稿 → `publishBlocker` → 事务外检查 → 开事务 → 加锁 → 过期检查 → 事务内检查 → 改状态 → 发布后动作 → 审计。** 发布必须能在调用方传入的事务里执行（`publishPassthrough` 要用）。流程本身的错误（不是草稿、已发布、草稿被改过、没有草稿可丢弃，一律 400）都继承 `PublishError`，各种可发布项自己的错误类也继承它。`publishReason`、`publisherCount`、`publishBlocker` 由这个模块导出，页面显示的原因和发布时的拦截出自同一处。

没有合成一张通用版本表（像 ADR-0025 的 `dsl_versions` 那样），因为这次只想把代码收到一处，迁移数据的代价与收益不成比例。也没有做内存适配器来测试：这套流程的核心是 PG 的行锁与事务，假实现测不出锁的顺序。

## Consequences

- 新增一种可发布项只需写一个适配器，不要再自己写一遍发布流程。
- 审计一律在发布后动作（入队）之后；映射、指标与标签、合并组、自定义实体的审计位置因此后移。
- 合并组改为只在新建版本时写审计，和其他可发布项一致（以前每次保存都写 `merge_group.saved`）。
- 发布统一返回发布后动作的结果（任务或 `null`），丢弃统一返回 `{kept}`；指标与标签、模板定义原来返回的 `{published}` 跟着改。
- 映射的停用和恢复、指标与标签的回填、重算与删除、`enableDefaultTemplates`、自定义实体的删除，不属于这个模块。
- 发布流程的集成测试只在这个模块写一套；各种可发布项的测试只保留它们自己的校验和发布后动作。
