# 分析计划：对话里的结构化产物，由服务端确定性校验

AI 助手回答「近 30 天各城市高价值消费者的退款率」这类问题时，要在几个相近的指标里选对口径，判断现有定义能否直接回答，并且不越过平台的能力。原先完全靠模型自己判断。决定：助手先提交一份结构化的**分析计划**，由服务端确定性地校验，再走现有入口执行（ADR-0003、ADR-0043 不变）。

**计划是对话里的产物。** 助手新增工具 `validate_plan`：模型提交计划 JSON，包括模式、选中的条目（标识、版本、语义哈希）、粒度、维度、人群、时间含义、步骤、假设与要问的问题。计划随对话加密保存（ADR-0043），不新建表，也不做状态机。租户、操作者与权限由服务端注入，不信任 JSON 里的值。

**五种模式。** `reuse_result`：用已有结果回答，指向现有页面或接口，不新增助手读取结果的工具。`draft_definition`：起草 DSL，保存为草稿，照旧双人发布。`draft_query`：起草工作台 SQL，填进编辑器，由成员执行。`clarify`：追问。`unsupported`：平台表达不了，说明原因与可行的下一步。

**四类检查**，结果是 valid / needs_clarification / unsupported / invalid，并附上问题出在哪里：

- **硬性检查**：引用的标识必须来自本次检索结果，成员有权限，条目仍然有效，版本与语义哈希和当前一致。不通过就是 invalid。
- **口径检查**：用户明确要求的单位、时间含义、窗口与所选定义的口径声明（ADR-0046）不相容，就不允许 `reuse_result`。口径声明是「未知」或需复核的，返回 needs_clarification，不当作匹配。
- **可加性检查**：比率、去重计数、最新值这类指标，不能在分组上直接求和或平均。
- **平台能力检查**：DSL 只能算到统一消费者粒度，按城市等其他粒度汇总只能走 `draft_query`，否则就是 unsupported。

维度路径的基数检查与数据新鲜度检查放到试点之后。

**执行前再校验一次。** 存草稿、填入工作台之前，用当前元数据重新校验计划，顺带发现过期的计划（依赖变了、权限变了），所以不需要单独维护「过期」状态。

没有选「新建 `analysis_plans` 表 + 完整状态机 + 绑定计划版本的确认令牌」：首期这些没有用处，有价值的是校验逻辑本身。等出现计划要跨对话共享、审批或定时执行的需求，再升级。

## Consequences

- 校验是确定性的，用普通的 vitest 测，进 CI；计划模式选得对不对，用 `pnpm eval:requirements` 评测。
- 助手每轮工具调用上限（`MAX_TOOL_CALLS`）里要给检索、展开、校验与保存都留出次数。
