# 映射可以读已发布的源视图：不增量，视图版本或它引用的表有新批次时由全部批次重建

ADR-0022 让数据工程师写源视图，#96 让映射以它为输入。映射原来只读一张源表，合并按这张表的变更批次增量进行（ADR-0006、ADR-0015）。视图可以连接多张表，增量的前提不再成立，下面定下视图映射怎么写、怎么合并、什么时候合并。

**写法。** 映射 YAML 里用 `view: <视图名>` 代替 `table:`，两者必须且只能写一个。视图名在数据源内唯一，与同名的源表互不混淆（`mappings.source_view_id` 指向视图，`table_name` 存视图名）。只能引用**已发布**的源视图，字段对照的是视图最新已发布版本的输出列（平台列除外）。这些列在保存视图草稿时由 `DESCRIBE` 得到，与引用的原始层表一起存进 `source_view_versions.columns` / `tables`，保存映射时不用挂载数据湖。早于本决定保存的视图版本没有这两项，要重新保存并发布一版才能被映射引用。没有这两项的旧草稿不能直接发布，要先重新保存一次。

视图没有同步维护的主键（`_keys`）。映射可以写 `view_key: [列, …]` 声明视图里标识一条记录的列（通常是主表的主键），合并时按它取每条记录的最新一版，与有主键的源表相同。不写时按整行区分记录，与没有主键的源表相同。主表有主键时应写 `view_key`。不写的话，主表的一次更新会被当成一条新记录，旧版本留在当前记录里。

**合并读视图最新的已发布版本。** 入队合并时把视图最新的已发布版本（版本号、SQL、引用的表）放进任务参数，工作进程不读平台库。执行前按 ADR-0022 的规则再校验一次 SQL：合并的会话不是只读挂载，这一步挡住保存后才出现的绕过方式。之后在 `USE lake.bronze_<数据源 ID>` 下把视图的结果物化进会话的本机库 `stage`，再照源表走同一套步骤（取最新一版、转换、去重、写标准层）。空跑同样读视图最新的已发布版本，不读草稿。视图引用的表有还没同步进原始层的，合并与空跑都跳过并说明原因。

合并与空跑读的是明文原始层，不像预览那样读敏感列已哈希的同名视图。视图执行出错时，报错里引号中的字面量一律抹成 `***` 再写进任务结果或页面，类型转换等报错不会带出取值。

**不增量，有变化就重建。** 视图的 `_batch` 取自作者选的那张表，各表的批次号各自递增、不能比较。连接的码表变了，主表的行不会有新批次，按 `_batch` 增量会漏掉。所以视图映射每次合并都先算一个标记：`view_key`、视图版本，以及引用的每张表在原始层的最大批次。标记记在合并日志 `silver._merges` 的 `source_keys` 里，与上次相同就不读视图、记一条“无新批次”的合并，不同就由全部批次重建当前记录与这个映射在标准层的行。

**触发。** 沿用 ADR-0015 的三条路径，只把“同步给源表写入了变更”换成“同步给视图最新已发布版本引用的任一张表写入了变更”。同步后的合并与定时检查共用这个判断。源视图发布新版本时，为基于它的已发布映射入队一次合并，按新版本重建。发布时如果已有合并在运行，入队不了，就由定时检查补上：除了比较映射版本，它还比较最近一次合并参数里带的视图版本与视图最新的已发布版本。

**解密。** 视图可以连接、改写、聚合，按源表主键找不回视图的一行。基于源视图的映射不能申请解密，请在读源表的映射上解密（ADR-0005）。

## 已接受的取舍

- 每次有变化都全量重建，开销随原始层历史增长，ADR-0015 拒绝全量重算的理由在这里成立。视图映射适合码表连接、宽表拆分这类中小规模的整理；很大的表请直接映射源表。等真遇到瓶颈，再考虑对只引用一张表的视图做增量。
- 视图读的是原始层的变更日志，不是当前状态。连接码表时要由作者在视图里取码表每个键的最新一版（并去掉删除），否则一个键会对出多行。平台不替作者做这一步。
- 引用的表和视图版本都没变时不重读视图，所以视图 SQL 里依赖当前时间（`now()`）的逻辑不会自己刷新。
- 视图可以把敏感列改名后映射到没标敏感的扩展字段，明文就进了标准层。这与读源表的映射把敏感列映射到不敏感的扩展字段是同一个风险。视图没有列统计，表单不会按格式提示这一列像敏感信息，要靠作者与发布者在双人发布时把关。
- 同名的源表与源视图映射到同一个实体，会撞上 `(source_id, table_name, entity)` 唯一约束，要改视图名。
