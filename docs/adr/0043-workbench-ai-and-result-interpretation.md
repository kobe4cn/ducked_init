# 工作台 AI 起草查询与结果解读：成员确认后才发送结果行

ADR-0003 否决的是由模型在运行时产出结果；工作台（ADR-0036）本来就是给人用的自由 SQL 通道。决定：AI 可以在工作台**起草 SQL**，由成员查看后自己执行；成员也可以主动请 AI **解读结果**：确认后才把结果的前若干行（剔除敏感列与哈希列）发给模型服务，审计记行数与列名、不记取值。结果只用于探索，不进快照、不对外服务，所以不违背 ADR-0003。平台内的 AI 助手不能执行查询（平台外 Agent 见 ADR-0042）。

**对话的存储。** 助手对话存在平台库，用租户信封加密（ADR-0009）；只有本人可见，可以只读分享给同租户成员，成员被移出租户时随之删除。**结果行一律不存**，只存 SQL、行数、列名与解读文字，回看时按 SQL 重新执行。原因：结果行是业务数据，按 ADR-0002 不能落在平台库；存了也会成为删除请求（ADR-0020）擦不到的副本。

**解读发送什么。** 成员点「请 AI 解读」后，服务端按 SQL 重新执行、列出将发送与剔除的列，成员确认后再执行一次（不信客户端传来的行），只发前 50 行。三条剔除规则：系统列；名字像敏感字段的列（`looksSensitive`）；前 50 行里有取值含 64 位十六进制哈希的列。结果列无法回溯到字段（别名、表达式都会改名），所以按列名和取值保守剔除：`SELECT phone AS p` 的 `p` 靠取值规则剔除，`consumer_id` 这类本身就是 sha256 的列也一并剔除。每格最多 200 字。

## Consequences

- 残留风险：解读文字里可能写出个别取值。提示词要求解读只谈聚合规律、不点名个人，但不能保证做到。
- 残留风险：取值规则只认完整的 64 位哈希，`substr(phone, 1, 10)` 这类截短的哈希片段换个列名就拦不住；解读时成员要在确认框里自己看清发送的列。
