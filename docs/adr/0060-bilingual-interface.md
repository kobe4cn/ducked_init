# 界面双语：中文原文当翻译键，文案在展示时按界面语言翻译

平台要同时支持中文和英文界面。现有约 3300 条去重后的中文文案写在代码里，其中服务端报错约 580 行，测试里约 2400 行断言涉及中文。我们决定保留中文原文作为翻译键，只另外维护一份英文词典，文案在展示时按读者的界面语言翻译。

**翻译机制。** 代码用一层很薄的 `msg()` / `t()` 包住中文句式，变量作为参数传入（`msg('映射 {id} 不存在', { id })`）。`Error.message` 仍是中文，所以现有测试基本不用改。单复数和变量格式交给 `intl-messageformat`。英文词典分服务端和前端两份，前端词典只在英文界面加载。中文句式改动后英文词典缺键时，由自动检查拦下。

**入库的文字。** 后台进程写入时不知道谁会来读，所以新数据（如任务失败原因）在原有中文之外另存句式和参数，展示时按读者的语言翻译。旧数据没有这些信息，显示中文原文，不做回填。审计日志本来就存动作和明细、展示时才拼句子，历史记录也能翻译，明细里的自由文本除外。

**界面语言。** 一个人只有一种界面语言：`members.locale` 可空，切换时同步更新同一邮箱的所有成员记录，因为一封登录邮件会列出该邮箱所在的全部租户。优先级是账号 > cookie > 浏览器语言 > 中文。界面语言只决定平台自身文字和数字日期的写法，不改变租户数据、时区、货币和数值。字符串排序仍按 ADR-0045，不随语言变化。

**翻译边界。** 界面、报错、邮件、审计日志和平台内置名称（标准字段名、模板名、枚举、RFM 默认人群名的展示）都翻译。客户数据和成员录入的内容不翻译。字段同义词表匹配的是源表列名和取值，与界面语言无关，不翻译。标准模板包本期不翻译。映射 YAML 模板的注释按创建时的界面语言生成，保存后属于租户内容。指标口径说明在页面上跟随界面语言，进检索和模型上下文的部分固定用中文，检索数据不按语言存两份。

**AI 助手与检索。** 回复跟随界面语言，成员在问题里明确指定时除外。工具说明、工具返回和知识库保持原文。英文检索靠三处补齐：标准字段自带英文检索词；AI 起草入口遇到非中文需求时，先由模型转成目录用的中文词再检索；时间范围识别补上英文说法。

**对外接口。** `/api/v1` 默认仍返回中文，请求带 `Accept-Language: en` 时返回英文，并新增人工命名的稳定 `code` 字段。`/mcp` 不变，它的读者是外部 Agent。

**上线方式。** 全部完成前用环境变量关闭英文入口和浏览器语言判断，避免成员看到中英混杂的页面。CI 用棘轮检查保证未接入翻译的中文数量只减不增。`/ops` 在正式开放之后单独完成。

## Considered Options

- **为每条报错命名错误码**：约 580 条都要起名并维护中英两份文案，断言中文的测试也要改。只有对外接口需要稳定的码，所以只在 `/api/v1` 使用。
- **i18next**：功能齐全，但默认按命名的键组织文案，和中文原文当键的做法不契合。
- **Lingui**：同样支持原文当键，但依赖编译插件，项目目前没有 Babel 流水线。
- **语言偏好按租户分别保存**：同一邮箱的登录邮件无法确定语言。

## Consequences

- 改中文文案就是改翻译键，必须同步更新英文词典。
- 中文句子不能再用碎片拼接（如 `${label}必须是数字`），英文语序不同，要改成完整句式。
- 代码不能再依赖报错文字做判断，要改用结构化字段。
